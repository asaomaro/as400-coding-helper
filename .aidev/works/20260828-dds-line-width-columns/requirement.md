# 要件: 行長の数え方を実機の桁に揃える

## 背景 / 課題

行長の上限（100 桁）は lint も編集も **JS の文字数**で数えている。
DBCS を含む行は実機ではもっと長い——DBCS の連なりの前後に SO/SI が 1 桁ずつ入り、
全角 1 文字は 2 桁を占める。

**実機で確かめたところ、黙って壊れていた**（IBM i 7.3）:

- 全角 30 文字の定数を持つ行（**JS では 76 文字**）をメンバーに入れると
  **切り捨てられ、読み戻すと 71 文字**になっていた。lint は何も言わない。
- キーワード欄の折り返し（`foldKeywordArea`）も JS の文字数で数えており、
  **実機がコンパイルを通さない欄を書き出していた**（全角 17 文字の定数は
  JS 19 文字なので「36 桁に収まる」と判定されていたが、実機は 38 桁で弾く）。

`20260826-dds-attribute-editing` の `decisions.md` D7 で「決める」として起票してあった。

## 目的 / ゴール

桁を数えるところが**実機の桁**（`printWidth`）で揃っている状態。
書き出したものが実機で通り、通らないものは指摘が出る。

## ユーザーストーリー

- US1: 日本語を含む DDS を書く人として、実機で切れる行は指摘してほしい。
  なぜなら切れたことに気付くのは**転送してコンパイルした後**で、
  そのときには何文字消えたのか分からないから。（受け入れ: AC1, AC2）
- US2: 同じ人として、デザイナが書き出した行は**必ず通る形**であってほしい。
  なぜなら自分で書いていない行を直すのは、書くより難しいから。（受け入れ: AC3, AC4）

## スコープ

### 対象
- lint の `line-length`
- 編集の上限（`line-too-long`）
- キーワード欄の折り返し（`foldKeywordArea`）

### 対象外
- **上限の値そのもの**（100 桁）は変えない。数え方だけを直す。
- ソース物理ファイルのレコード長に応じた上限（80 / 100）の出し分け。
  実機のファイルごとに違い、ローカルからは分からない。

## 完了条件 (受け入れ基準)

- [ ] AC1: 全角を含む行の桁が**実機の桁**で数えられる（SO/SI ＋ 全角 2 桁）。
- [ ] AC2: 指摘の文言に実機の桁と JS の文字数の**両方**が出る（違いが分かる）。
- [ ] AC3: 折り返しの各塊が実機の桁で 36 を超えない。
- [ ] AC4: 折った結果が**実機でコンパイルを通り**、読み直すと同じ値に戻る。
- [ ] AC5: 半角だけの行の振る舞いは変わらない（回帰）。

## 相互作用の受け入れ基準

- [ ] AC-I1 下線の位置: 指摘の下線は**溢れ始める文字**から引く
      （エディタの列は JS の添字なので、桁とは別に求める）。
