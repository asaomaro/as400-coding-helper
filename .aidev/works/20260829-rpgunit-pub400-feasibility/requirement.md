# 要件: RPGUnit の pub400 導入可否を確かめる

## 背景 / 課題

設計書（`docs/workflow/ibmi-dev-workflow.md`）はユニットテスト層に **RPGUnit ＋ `@ibm/itest`** を
置いている。だが**実機に入れられるかが未確認**のまま、依存する項目
（「固定長（P 仕様書）で RPGUnit テストが書けることを実機確認する」）も止まっていた。

出所: `.aidev/backlog/workflow.md`。

## 目的 / ゴール

**pub400 に RPGUnit を入れられるかどうかが、根拠つきで決着している状態。**
入れられないなら、**なぜ**と**どこでなら入るか**が分かっている状態。

紐づく charter ゴール: 「横断する技術的負債の解消」（設計書の前提の検証）。

## ユーザーストーリー

- US1: **ユニットテスト層を作ろうとする開発者**として、RPGUnit が pub400 で使えるかを
  先に知りたい。なぜなら、**使えないなら設計書のユニット層ごと組み替え**が要り、
  試してから分かるのでは遅いから。（受け入れ: AC1, AC2, AC3）

## スコープ

### 対象
- pub400 で RPGUnit の導入経路が通るかを**副作用の無い方法で**確かめる。
- 通らないなら理由を特定し、代替経路の可否も見る。
- 依存している項目の前提を書き換える。

### 対象外
- **実際に RPGUnit を入れること**。起票は pub400 が対象で、そこが不可なら
  別の機械に第三者のバイナリを入れる判断は**別の話**（利用者が決める）。
- `@ibm/itest` の実行（導入が前提）。

## 完了条件 (受け入れ基準)

- [ ] AC1: pub400 で導入できるか**できないか**が、実機の応答（メッセージ ID）で決着している。
- [ ] AC2: できない場合、**標準経路と代替経路の両方**について理由が示されている。
- [ ] AC3: **他の機械での可否**も測ってあり、次の判断材料になっている。
- [ ] AC4: 依存する項目（P 仕様書での RPGUnit）の前提が書き換わっている。
- [ ] AC5: 確認は**副作用が無い**（オブジェクトを作らない・消さない）。
