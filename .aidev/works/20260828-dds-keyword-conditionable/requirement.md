# 要件: 条件付けできないキーワードを知らせる

## 背景 / 課題

DDS は条件が付く対象を「フィールド**または**キーワード」とするが、
**キーワードごとに可否が決まっている**。付けられないものに条件標識を付けたソースは、
実機がコンパイルを通さない（`CPF7311`。`20260827-dds-conditional-edtcde` で
`EDTCDE` / `EDTWRD` / `CHECK` を実測）。

いまのデザイナと lint は**何も言わずに描く**。壊れたと気付くのは実機に持っていったとき。

しかも直前の work（`20260827-dds-keyword-condition-edit`）で**条件を付ける手段を足した**ので、
デザイナから通らない形を作れるようになっている。

## 目的 / ゴール

**条件を付けられないキーワードに条件を付けたら、その場で分かる状態。**

紐づく charter ゴール: DDS の視覚的な確認と編集（第 4 の柱）。

## ユーザーストーリー

- US1: DSPF / PRTF を書く開発者として、**コンパイルが通らない形をその場で知りたい**。
  なぜなら実機に持っていって `CPF7311` を見てから戻るのは往復が大きいから。（受け入れ: AC1, AC4）
- US2: この PJ を保守する開発者として、**可否の表を手で持ちたくない**。
  なぜなら 200 以上あり、手で書けば必ずずれるから。（受け入れ: AC2, AC3）

## スコープ

### 対象
- 原典から可否の表を**生成**する
- 描画の指摘（デザイナ）と lint 規則
- 画面ファイルと帳票の両方

### 対象外
- 編集で**拒否**する（`decisions.md` D3）
- 物理/論理ファイル（条件付け欄の意味が違う。デザイナの対象外）

## 非機能要件 / 制約

- 表は**手で書かない**（AGENTS.md）。原典の各キーワード詳細ページから生成する。
- 原典が可否を書いていないキーワードは**咎めない**。
  「知らない＝付けられない」にすると、実機で通るソースを弾く。

## 完了条件 (受け入れ基準)

- [ ] AC1: 条件を付けられないキーワードに条件が付いていたら指摘する
- [ ] AC2: 可否は**原典から生成**する（手書きの表を持たない）
- [ ] AC3: 生成結果が**実機で確かめた 5 件**と一致することを機械検査する
- [ ] AC4: lint 規則として CI でも落ちる（既定 ON・error）
- [ ] AC5: 原典に記述が無いキーワードは指摘しない
- [ ] AC6: 代表行のキーワード（項目自身の条件で決まる）は指摘しない
