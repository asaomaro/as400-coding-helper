## 実装方針

**検査を先に強くしてから直す**のが筋だが、今回は**先に欠落を見つけてしまった**ので
（別の work の調査中に `CF03` が引けないことに気付いた）、直したあとで
**修正前のデータを新しい検査にかけて落ちること**を確認し、検査が効くことを示す。

## 作業順序と依存関係

1. 生成側 2 本の名前の取り出しに `nn` を許す（依存: なし）

4. 再生成の前後を突き合わせ（追加 2 / 削除 0 / 変更 0）（依存: 3）
5. 検査に名前の突き合わせを足す（依存: なし）
6. 修正前のデータで検査が落ちることを確認（依存: 5）
7. README の件数を更新（依存: 2）

## リスク / 留意点

- **生成は 2 段**（索引 → 構文）。`generate-dds-keywords.mjs` だけを走らせると
  `syntax` / `hasParameters` が**消える**（別スクリプトが後から足しているため）。
  必ず `generate-dds-keyword-syntax.mjs` まで走らせる。**実際に一度踏んだ。**
- 検査の「名前の形」が `^[A-Z][A-Z0-9]*$` のままだと、`CAnn` を**不正な名前**として弾く。
- 詳細ページは `manifest.yml` に載っていない（索引ページだけが載っている）。
  今回も載せない（既存の扱いに揃える）。取得元は `README.md` の表と本 work の記録に残す。

## テスト方針

- `node docs/origin/verify-dds-keywords.mjs`（強化後）が通る。
- **修正前のデータで落ちる**ことを確認する（検査が効いている証拠）。
- `npm run verify`（14 項目）が通る。
- 再生成の前後を機械的に突き合わせ、**既存 174 件が 1 件も変わっていない**ことを確認する。
