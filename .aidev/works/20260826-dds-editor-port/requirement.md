## 背景 / 課題

- `main` には既に **DSPF/PRTF のレイアウト解決・プレビュー・レイアウト診断（lint）**がある
  （`core/dds/dspfLayout.ts` / `language/dspfPreview.ts` / `lint/rules/layout.ts`、2026-07 の PR #101〜#107）。
  プレビューは項目を掴んで動かせるが、**できるのは移動だけ**（`dspfPreview.ts:135` の `move`）。
- 書き戻しは**位置欄（39-44 桁）の文字列置換**（`core/dds/ddsPositionWriteBack.ts`）。
  **長さの変更・項目の追加・削除には手段が無い。**
- SDA 相当の作業＝「レイアウトを組む」には移動だけでは足りない。**新しく項目を置く・長さを変える・消す**が要る。
  今は結局 SEU/SDA に戻ることになり、VSCode の開発フローが分断されたままになる。
- **操作を増やすほど「触っていない行が変わらないこと」の保証が必要**になる。
  位置欄限定の書き換えは事故が起きにくいが、追加・削除まで広げると**構造的な保証**が無いと壊れる。
- 素材はある: **PR #108（draft）**に、`raw` 保持でバイト不変を構造的に保証するモデルと、
  4 操作＋検証つき適用が実装済み（実機で確定した規則・テストつき）。
  ただし **`main` を知らない古いツリーの上で作られた**ため、そのままでは DDS の判定が二重になる。
  **`main` を土台に、必要なものだけ移植する**（PR #108 のコメント参照）。

## 目的 / ゴール

達成したい状態:

- **DSPF のレイアウトを、桁を数えずに GUI 上で「組み立てられる」状態**
  （移動だけでなく、長さの変更・項目の追加・削除ができる）。
- **編集しても、触っていない行が 1 バイトも変わらないことが構造で保証されている状態**
  （実装の注意深さに依存しない）。
- **規則違反を生む編集は適用前に止まり、理由が利用者に見えている状態**
  （実機コンパイルまで気付けない、が無くなる）。
- **DDS の桁・規則の真実源が 1 つのままである状態**（編集能力を足しても判定を二重に持たない）。

紐づく charter ゴール: **「DDS（DSPF/PRTF）の視覚的編集」**——現 charter は 3 本柱
（プロンプター / ルーラー / SOSI）のままで、既にマージ済みの DDS プレビュー・lint も反映されていない。
**本 work で charter を実態に合わせて更新する**（ユーザー判断 2026-08-26）。

- **US3**: 開発者として、規則違反を生む編集は**適用前に止めて理由を見せて**ほしい。
  なぜなら **実機コンパイルまで気付けないと往復のコストが高い**から。
  一方で、**元からある違反を理由に編集を止められては困る**——直すために動かしたいのだから。（受け入れ: AC6, AC7）

## スコープ

### 対象

- **DDS の構造化モデルと書き戻し**：行の `raw` 保持、解釈できない行の素通し、桁範囲の局所置換。
- **編集操作 4 種**：移動 / 長さ変更 / 追加 / 削除。適用前の検証つき。**部分適用しない。**
- **VSCode 非依存のビジュアルエディタ**（キャンバス UI ＋ ホストの継ぎ目）から 4 操作を使えるようにする。
  - UI は `vscode` にも `acquireVsCodeApi` にも触らない。ホストとの会話はメッセージだけ。
  - VSCode 側は `CustomTextEditorProvider`（`priority: "option"`）として載せる。
  - **単独起動ハーネス**を用意し、同じ UI が VSCode 無しで動くことを実際に確かめる。
- **符号位置の修正**：`35 桁 = S` かつ入力可（`38 桁 = B`/`I`）のフィールドは占有が **+1 桁**。
  実機で 8 通り確かめた事実（`research.md` F19）だが `main` に入っていない。
  **回帰テストの期待値更新までを範囲に含める**（既存診断の結果が変わりうるため）。
- **charter の更新**（実態に合わせる）。

### 対象外（本 work ではやらない）

- **実機ゴールデン比較**（ts5250 で採取した画面と描画を突き合わせる）— 後続 work。
- **CLI の拡張**（`parse` / `render` / `validate` / `patch` / `init`。現 CLI は lint のみ）— 後続 work。
- **既存プレビューの編集対応** — プレビューは読むための器として現状維持（編集はエディタ側）。
- **単独起動の製品化**（ファイル操作・undo を備えた独立アプリ）— ハーネスは検証用に留める。
- **PRTF の編集**（プレビューは現状維持。本 work は DSPF のみ）。
- **キーワード編集・条件標識の編集**（L2 以降）。
- npm workspaces 化・パッケージ分割（`main` の単一パッケージ構成を維持する）。

## 機能要件

1. 固定長 DDS を構造化モデルに変換し、書き戻せる。**編集していない行はバイト単位で不変。**
2. 解釈できない行（コメント・継続行・未対応キーワード）は保持し、書き戻しで失わない。
3. **移動 / 長さ変更 / 追加 / 削除**の 4 操作を、モデルに対する操作として適用できる。
4. 適用前に検証し、**規則違反を新たに生む操作は拒否**する。**警告レベルでは拒否しない。**
5. 複数操作のうち 1 つでも拒否されたら、**何も適用しない**。
6. DSPF プレビューの UI から 4 操作ができ、拒否されたときは理由が読める。
7. 判定（幅・重なり・桁溢れ・属性文字の占有）は **`core/dds` の既存実装を使う**。再実装しない。

## 非機能要件 / 制約

- **真実源を増やさない**。`core/dds/dspfLayout.ts`・`ddsPositionColumns.ts`・`ddsFieldWidth.ts`・
  `editCode.ts`・`dspfScreenSize.ts`・`core/dbcs.ts` が既に持っている規則を土台にし、
  モデル層はその上に載せる。**同じ規則を 2 か所に書かない。**
- **既存挙動を壊さない**（charter 品質基準）。プレビューの従来操作・lint・診断・アウトライン・補完。
- **`vscode` 非依存の層は `src/core/` の規約に従う**（文字列 → 文字列。単体テストは `vscode-stub` 経由）。
- **単一パッケージ構成を維持**する（`main` は workspaces を使っていない）。
- `npm run verify`（原典検証 `verify:defs` ＋ roundtrip）と `npm test` を通す。
- 仕様の根拠は **IBM 原典**（`docs/origin/dds/`）を正とし、実機（`ibmi-remote` skill）での確認を併用する。
- **1 PR = 独立してレビュー可能な粒度**（charter）。本 work に収まらない分は後続 work へ切る。

## 相互作用の受け入れ基準

- [ ] **AC-I1 開く / 閉じる**: 追加は「追加モード」を開始してからキャンバスを指して置く。
      `Esc` でモードを抜けられ、抜けたときは**何も追加されていない**。
- [ ] **AC-I2 確定 / 取り消し**: 長さ変更はドラッグを離した時点で確定する。
      **拒否されたら見た目が元に戻る**（適用されたように見えたまま残らない）。
- [ ] **AC-I3 キーボードだけで完結**: 項目を選び、矢印キーで 1 桁ずつ動かし、`Delete` で削除できる。
- [ ] **AC-I4 フォーカスの行き先**: 拒否の理由は**フォーカスを奪わない場所**に出る。
      追加モードの開始でキャンバスへフォーカスが移り、`Esc` で元の位置へ戻る。
- [ ] **AC-I5 既存の操作を妨げない**: 既存の移動・該当行へのジャンプの操作感を変えない。
      新しいキー（`Delete` / 矢印）は**キャンバス上の選択がある時だけ**効き、他へ漏らさない。
