# 決定記録

## D1: 編集の戻り値を「旧行の範囲＋置き換え後の行」にした

- 背景: 「適用後テキスト＋変更範囲」を返す設計は、**その範囲を旧文書の座標として使った時点で
  行数が変わる操作（追加・削除）で壊れる**。別実装で実際に踏んでいる
  （`feature/dds-visual-editor` の `07-editor-webview/review.md` must-1: 削除で行が消えず後続行が複製された）。
- 決定: `DdsEditResult = { replaceFrom, replaceTo, lines }`。**旧範囲と新行を別々に返す。**
- 理由: 座標の取り違えが**起こりようがない**。差分計算も要らず、呼び出し側は `Range` に写すだけ。
- 影響: 削除は `lines: []`、挿入は `replaceFrom === replaceTo`。3 つの形が型から読める。

## D2: 編集の宛先は `sourceLine`。合成 ID を持たない

- 背景: 別実装は `${様式}#${通番}` の合成 ID を使い、**構造変更で振り直されて別の項目を指す**
  事故を起こした（同 review should-2。削除の直後にもう一度 Delete を押すと別の項目が消える）。
- 決定: `DspfPlacedItem.sourceLine` をそのまま宛先にする。
- 理由: 行が消えれば宛先も消えるので、**同じ事故が構造的に起きない**。
  UI 側も「構造変更後に選択を捨てる」だけで足りる。

## D3: 削除の単位は論理単位。規則は `ddsLogicalUnits` に置いた

- 背景: DDS の項目は 1 行とは限らない（キーワード継続行は直前に付き、条件付け行は次に付く）。
  代表行だけ消すと**継続行が孤児として残る**。
- 決定: `LogicalUnit` に `sourceLines`（その単位に属する行・1 始まり）を足し、削除はそこから作る。
  注記行・空行はどの単位にも属さないので**消さない**——結果として範囲は連続とは限らず、
  だから `applyDdsEdits` は**配列**を返す。
- 理由: 規則を編集側に書き写すと、描画側（`dspfLayout`）とずれる。**共有モジュールに置く**。
- 影響: `unitItemKind`（定数かフィールドか）も同じ理由で共有に切り出し、`dspfLayout` と `ddsEdit` が使う。

## D4: 拒否するのは「ソースに書けないもの」だけ

- 背景: requirement は当初「規則違反を生む操作は適用前に拒否」としていたが、
  **既存のプレビューは移動を無検証で適用**し、違反は診断で見せている（`research.md` F16）。
  そのまま拒否を導入すると既存挙動が変わる。
- 決定（ユーザー判断 2026-08-26）: **書けないものだけ拒否**（長さ欄に収まらない・宛先の行が無い・
  定数に長さ等）。重なり・はみ出し・1 桁目は**適用して診断で見せる**。
- 理由: 「直すために動かしたい」が成立する。元からある違反が編集を凍らせない。
- 影響: `DdsEditRejectionCode` は 6 種すべて「書けない」もの。requirement の AC6 / AC7 を改訂した。

## D5: 符号位置は `width` ではなく `occupancy` と はみ出し判定に入れた

- 背景: 実機で確かめた事実——**35 桁が `S` かつ 38 桁が `B`/`I` なら占有が +1 桁**（`research.md` F19）。
  `main` の `fieldWidth` はこれを加算していなかった。
- 決定: `dspfLayout` の `occupancy` と `dataEnd`（はみ出し判定）に入れる。**`fieldWidth` には足さない。**
- 理由: `width` は**描画にも使われている**。符号位置は画面上は空白なので、
  描画幅に含めると**存在しない文字を描く**ことになる。
- 影響: 既存の 448 テストは 1 件も壊れなかった（影響は符号付き入力フィールドの隣接・はみ出しだけ）。
  実機 8 通りの表を回帰テストにした（`test/unit/dspfSignPosition.test.ts`）。

## D6: 編集の器を「既存プレビューの拡張」から「VSCode 非依存のエディタ」に変えた

- 背景: 当初は既存プレビュー（`showDspfPreview`）に 4 操作を足す計画で、実装も一度通した。
  だが**既存プレビューは VSCode 専用の作り**（サーバ側で HTML を組み立て直し、状態を持たない）で、
  **単独で動かす思想が無い**。本 PJ が目指すのは「VSCode は埋め込み先の 1 つ」。
- 決定（ユーザー判断 2026-08-27）: **今回開発するものを主体**に据える。
  - UI は素の web（`src/dds/webview/ui.ts`）。`vscode` にも `acquireVsCodeApi` にも触らない。
  - ホストとの会話は `protocol.ts` のメッセージだけ。`acquireVsCodeApi` は `bridge.ts` の 1 か所。
  - VSCode 側は `CustomTextEditorProvider`（`priority: "option"`）。**既存プレビューは 1 行も変えない。**
  - 単独起動ハーネス（`dev/`）を用意し、**同じ UI が VSCode 無しで動くことを実際に確かめる**。
- 理由: 継ぎ目は**使わないと腐る**。片方のホストでしか動かさない分離は、いつの間にか片方に依存する。
- 影響: 一度書いたプレビュー側の編集実装は**破棄**した（`git checkout` で戻した）。
  requirement / spec / plan / tasks を改訂し、経緯を残した。
  `main` の資産（`core/dds` の規則・診断・論理単位・書き戻しの流儀）は**そのまま土台**として使っている。

## D7: UI に文字を数えさせない（区切りは core が渡す）

- 背景: DBCS は SO/SI が桁を消費するので、リテラルを開始桁にそのまま置くと**1 桁ずれる**。
  かといって UI に全角判定を持たせると、桁の真実源が 2 つになる。
- 決定: `RenderItem.segments`（文字と占有桁数の対）を core が計算して渡す。UI は
  `cols × セル幅` の箱に流すだけ。区切りの合計が `printWidth` と一致することをテストで固定した。
- 影響: フォントが全角を 2 セル幅で描かない環境でも**桁はずれない**（字が欠けることはある。
  CSS で `overflow: hidden`。桁の正しさを優先した）。

## D8: WebView 資産は esbuild で束ね、拡張ホストは tsc のまま

- 背景: `main` はバンドラを使わず tsc だけ（`out/` をそのまま VSIX に入れる）。
  一方 WebView はブラウザで動くので 1 ファイルに束ねる必要がある。
- 決定: **WebView と単独起動ハーネスだけ**を esbuild で束ね（`esbuild.webview.mjs`）、
  拡張ホスト側のビルドは触らない。出力は `out/dds-webview/`（VSIX に載る）。
- 理由: 既存のビルドの仕組みを丸ごと変えない。**変えるのは新しく足す部分だけ**にする。
- 影響: `devDependencies` に `esbuild` が 1 つ増える。型検査は `tsconfig.webview.json`
  （`lib: DOM` / **`types: []`**）で行い、**WebView から `vscode` を import する書き方が型で落ちる**ようにした。

## D9: 検証は「単体（CI）＋ 実操作 e2e（手元）」の二段構え

- 背景: WebView の中身は拡張ホストから触れない。HTML に文字列が含まれることを確かめても、
  **押して動くか**は分からない。
- 決定: core と純関数は単体テスト（CI で回る 487 件）。操作は**単独起動ハーネスを
  Playwright で実操作**する e2e（15 件・手元）。`playwright-core` は **devDependency にしない**
  （CI にブラウザが無く、入れると「CI に載っているのに走っていないテスト」が生まれる）。
- 影響: VSCode 側の器（`WorkspaceEdit`・undo・登録）だけが手動確認に残る。
