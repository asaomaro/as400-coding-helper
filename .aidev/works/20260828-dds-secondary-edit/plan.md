# 計画: 2 次画面サイズでの編集

## 実装方針

core（型 → 補助関数 → 検証 → 適用）を先に閉じ、UI は最後に繋ぐ。
core は VSCode に依存しないので、単体テストで受け入れ基準を全部確かめられる。

## 作業順序と依存関係

1. `unitRunEnd` / `conditionNameFor` を足す（依存: なし）
2. `move.screenSize` と `clearAlternatePosition` を型に足す（依存: なし）
3. 検証（3 つの拒否コード）（依存: 1, 2）
4. 適用（置換 / 挿入 / 削除）（依存: 1, 2, 3）
5. UI（掴む・矢印・Delete・resize を塞ぐ）（依存: 4）
6. e2e（依存: 5）

## リスク / 留意点

- **挿入で行番号がずれる**。同じ確定に複数の編集が乗るとき、後ろの編集の
  `sourceLine` が狂う。`applyDdsEdits` の結果は 0 始まりの区間なので、
  **適用側が並べ替えているか**を確かめてから足す。
- **1 次の経路を壊さない**。`screenSize` 省略時が既定という前提が崩れると、
  いままでの `move` が全部 2 次を見る。既存テストが守っているはず。

## テスト方針

- 単体: AC1-AC5 を `ddsEdit` の往復で確かめる。上書き行を作る形は
  **実機に通した形と一致すること**を固定する（`verify/` の probe と同じ桁）。
- e2e: 2 次の絵で掴んで動かし、1 次の位置が変わらないことを確かめる。
- 回帰: 1 次の `move` の既存テストが全部通ること。
