# 決定記録

## D1: 追加先の決定は「選択中の様式の見出し」を**行の見当より先**に見る

- 背景: spec の D2 では順序を「①行の見当 → ②選択中の様式 → ③末尾」と決めていた。
  実装して単独起動ハーネスで押したところ、**足した様式が選ばれ焦点も当たっているのに、
  キャンバスを押すと項目が別の様式に入った**（e2e の
  「足した様式にそのまま項目を置ける」が FAIL）。
  原因は順序そのもの——足したばかりの様式は項目が 0 件なので ① では絶対に引っかからず、
  既に項目を持つ様式が上に 1 つでもあると ① が必ず勝つ。**② には永久に到達しない。**
- 決定: 順序を **「①選択中の様式の見出し → ②行の見当 → ③末尾」** に変えた。
  ただし**見出しを選んでいるときだけ**で、項目を選んでいるときは ② のまま。
  併せて、見出しから置いたときは**置いたあとも同じ見出しを選んだままにする**
  （`place()` で `pendingSelectRecord` を立てる）。
- 理由 / 代替案:
  - **見出しを選ぶのは「この様式で作業する」という明示**だが、項目を選ぶのは
    その項目を見ているだけで置き先の宣言ではない。ここまで選択に寄せると、
    別の様式の行を押しても選択中の様式に入ることになる（既存の編集の振る舞いが変わる）。
  - 退けた案 1: **選択を常に優先する**（項目の選択も含む）。既存ファイルで
    「REC1 の項目を選んだまま REC2 の行を押す」が REC1 に入るようになり、悪化する。
  - 退けた案 2: **置いたあと必ずその様式を選ぶ**。行の見当で決まったときにも選択が生まれ、
    次のクリックの行き先が**静かに変わる**（今回と逆向きの同じ罠）。
    そこで「選択から来たときだけ選択を保つ」に絞った。
- 影響: spec.md の D2 と「受け入れ基準との対応」の AC4 の記述が実装と食い違う（順序が逆）。
  **spec.md を実装に合わせて直した**（review で突き合わせられるよう、この記録を残す）。
  受け入れ基準そのもの（AC4）は変わらない——むしろ D1 で初めて満たせた。

## D2: 検証は「様式の参照」と「項目の参照」の**両方**を対象にする

- 背景: requirement の AC11 は「削除した様式を指す参照（`&名前` / `CSRLOC` / `HLPARA(*FLD)`）」と
  書いているが、括弧の中は**項目を指すキーワードだけ**（`ddsReferences.ts` の `FIELD_ARGUMENTS`
  と規則 A）。様式そのものを指すキーワード（`SFLCTL` / `ERASE` / `PASSRCD` / `HLPRCD` /
  `MNUBARDSP` / `MNUBARCHC`）は挙がっていない。
- 決定: **両方**を検証タブに出す（`record-reference-not-found` / `field-reference-not-found`）。
- 理由 / 代替案: 様式を消せば、それを指す `SFLCTL(EMPDTL)` も、中のフィールドを指す
  `CSRLOC(...)` も**同時に**宙に浮く。片方だけ出すと「出ない側は正しい」と読まれる。
  AC11 の列挙は例示であって限定ではないと解釈した。
- 影響: AC11 は満たしつつ範囲が広い。既存ソースへの偽陽性が心配なので、
  **同梱の DDS を全部走査して 0 件**であることを単体テストで固定した
  （`ddsNewAndRecords.test.ts`。ファイルは列挙せずディレクトリを走査するので、
  サンプルが増えたら自動で対象になる）。

## D3: `fromLayout` / `fromPrtfLayout` の `outline` 引数から既定値を外した

- 背景: `records` の導き方を `outline` 由来に変えた（spec D1）。`outline` は既定値 `= []` を
  持っていたので、そのままだと**渡し忘れた呼び出しが `records: []` を黙って受け取る**。
- 決定: 既定値を外して必須にした。呼び出しは PJ 内 2 か所（両モデルの `build*RenderModel`）で、
  どちらも渡している。
- 理由 / 代替案: いま直している欠陥が**まさに「様式があるのに records が空」**なので、
  同じ状態を作れる口を残さない。既定値のまま「渡し忘れないこと」を散文で守る案は、
  守れなかったときに**静かに壊れる**（コンパイルは通る）。
- 影響: エクスポートされた関数のシグネチャが変わる。PJ 外の利用者は居ない（grep で確認）。

## D4: `requirement.md` の AC-I2 を AC7 に合わせて直した（T1）

- 背景: AC-I2 が「削除は**確認を経てから**消え」のままで、AC7（2026-09-08 に
  「確認ダイアログは出さない」へ書き換え済み）と矛盾していた。
- 決定: AC7 が後の判断なので、AC-I2 を「削除は**即座に効き**、undo で元に戻る」に直した。
- 理由 / 代替案: 矛盾したまま実装すると、review がどちらの AC と突き合わせるかで結論が変わる。
  research F8（この PJ に確認ダイアログは 1 つも無い）が AC7 の根拠なので、そちらを採った。
- 影響: 受け入れ基準の意味が変わる（確認ダイアログを実装しない）。要件本文に修正日と理由を添えた。
