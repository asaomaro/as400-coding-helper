# 決定記録

## D1: 上限の値域を「80 / 100 の 2 択」ではなく整数にした

- 背景: 起票時の決定（2026-08-29）は「`lineLength.maxColumn` を 80 / 100 から選べる」だった。
  根拠は `20260828-dds-line-width-columns` の D1 で、**pub400 の 5 件の標本**
  （92 が 3 件・112 が 2 件）に基づく見立てだった。
- 決定: **1〜32754 の整数**を受ける（`spec.md`「設計方針 1」）。
- 理由 / 代替案: research 工程で母数を実機カタログ全体（461,236 件）に広げたところ、
  レコード長は **171 種類**あり、`115`(データ 103 桁) / `132`(120 桁) / `120`(108 桁) などが
  実在した。上位 2 値で 98.1% を占めるが、**2 値の列挙では残りの環境で設定できない**。
  決定の意図（利用者が自分のソース PF に合わせられること）は整数の方がよく満たすので、
  意図に沿って値域だけ広げた。**ユーザーに確認のうえ変更している。**
- 影響: `requirement.md` の未確定事項がこれで解消。`package.json` は
  `enum` ではなく `type: integer` ＋ `minimum` / `maximum`。

## D2: `RuleContext.maxColumn` を必須にしたため、テストの共通ヘルパーを 1 か所変更した

- 背景: `plan.md`「リスク / 留意点」に「既存テストを 1 行も変えずに通ること（AC5）」と書いていた。
- 決定: `test/unit/lintRules.test.ts` の `context()` ヘルパーに `maxColumn` 引数
  （既定 `DEFAULT_MAX_COLUMN`）を足した。**import 行と合わせて 2 か所**。
- 理由 / 代替案: `RuleContext.maxColumn` を任意にすれば変更を避けられるが、
  **既定値が engine と規則の 2 か所に散る**。片方だけ直しても型は通りテストも落ちないまま
  食い違う（`RuleSpec.severity` を 1 か所にしか書かない理由と同じ）。
  必須にする方を採り、ヘルパーの機械的な変更を受け入れた。
- 影響: **既存テストの assertion は 1 つも変えていない**（追加 17 件・削除 0 件）。
  AC5 の実質——「既定のままなら指摘結果が変わらない」——は満たしている。
  `L >= 100` のメッセージは現在と文字列レベルで同一。

## D3: メッセージの注記域の案内を 3 分岐にし、原典を超えて主張しないようにした

- 背景: 既存メッセージの後半 `（1-80 桁が仕様書、81-100 桁が注記域）` は固定文言で、
  上限だけ差し替えると上限 80 のときに**存在しない注記域を案内する**。
- 決定: `describeColumns()` で 3 分岐にした（`L>=100` / `81<=L<=99` / `L<=80`）。
- 理由 / 代替案: 素直には「`81-{L} 桁が注記域`」と 1 本にできるが、
  **原典が規定するのは 81-100 桁目まで**で 101 桁目以降は書かれていない。
  `L = 103` で「81-103 桁が注記域」と言うと**原典を超えて主張する**ことになるため、
  上限が 100 以上のときは注記域を 100 桁までとしか言わない。
- 影響: `L >= 100` の分岐が既定 100 の現行文字列と完全一致するので AC5 に影響しない。

## D4: 不正値の扱いを経路で変えた（設定＝フォールバック / CLI＝エラー）

- 背景: 同じ「不正な桁上限」でも、設定経由と CLI 経由で最悪の結果が違う。
- 決定: 設定は `resolveMaxColumn()` で既定 100 にフォールバック。
  CLI は `UsageError`（終了コード 2）で落とす。
- 理由 / 代替案: 設定 UI にエラーを出す手立てが無く、**検査が黙って止まるのが最悪**。
  一方 CLI は明示的に渡した値なので、**黙って無視されるのが事故のもと**
  （既存の `--fail-on` / `--format` と同じ流儀）。
- 影響: `package.json` にも `minimum` / `maximum` を書き、設定 UI 側でも弾く（多層）。
