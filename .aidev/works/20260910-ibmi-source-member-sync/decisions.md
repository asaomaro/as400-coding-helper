# 設計判断: IBM i ソースメンバーの手動同期

## D1: Code for IBM i は実行時に検出する任意統合とする

- 状況: 本拡張の既存の固定長編集機能は IBM i 接続なしで利用できる一方、同期には既存の Code for IBM i 接続プロファイルが必須である。要件 AC4 は本拡張で接続情報を設定・保存しないこと、AC6 は未導入・未接続時に利用者へ理由を示すことを求める。
- 決定: `extensionDependencies` は追加しない。同期コマンドの実行時に `halcyontechltd.code-for-ibmi` を取得・必要なら activate し、export の `instance.getConnection()` と content API を検査する。型検査専用に `@halcyontech/vscode-ibmi-types` を開発依存へ追加し、実行時の npm import は行わない。
- 理由: 常時利用できる本拡張の既存機能を Code for IBM i の未導入で無効化せず、接続していない状態を AC6 の案内として扱える。公開 content API を使うため、資格情報、SFTP、IFS 一時ファイル、CCSID 変換を二重実装しない。
- 影響: 実行時 API の形が期待と異なる場合も接続なしと同じ成功扱いにせず、互換性エラーとして明示する。実機結合試験には Code for IBM i が導入・接続済みの VS Code 環境が必要となる。

## D2: ダウンロードは開いている文書を置換して保存する

- 状況: 要件 AC3 と利用者選択は、確認なしでローカル側を IBM i メンバー内容で上書きすることを求める。開いている文書だけを対象にするため、ディスクを直接書き換えるとエディターのバッファーとずれる。
- 決定: ダウンロード結果は対象 `TextDocument` の全範囲へ `WorkspaceEdit.replace` で適用し、成功時に `document.save()` でローカルファイルへ確定する。未保存のローカル編集もこの明示操作で置換される。アップロードは現在の文書バッファーの `getText()` を送る。
- 理由: 表示中のバッファー、保存済みファイル、フォーカスの整合を保ち、利用者が明示的に選んだ上書き方向をそのまま実現する。
- 影響: download の save が拒否・失敗した場合は、IBM i 側取得成功とローカル反映成功を混同せずエラー通知する。保存イベントを登録しないため、AC7 の自動同期禁止を守る。

## D3: 三層の一方向依存にする

- 状況: パス規則、外部拡張の可用性、VS Code UI 操作は変更理由も試験方法も異なる。1 つの command ファイルにまとめると、path の小さな変更にも VS Code と Code for IBM i の fake が必要になり、外部 API の更新影響も局所化できない。
- 決定: `memberPath`（純粋ドメイン）← `codeForIbmi`（外部 adapter）← `memberSync`（VS Code command）の一方向依存とする。command は `MemberContentApi` を注入可能な依存として受け、production 登録時だけ adapter を渡す。
- 理由: パス変換を VS Code 非依存で検証でき、adapter の動的 extension 検出を 1 箇所に閉じ、command の上書き・通知・フォーカス復帰を fake で検証できる。
- 退けた案: command から Code for IBM i の export を直接呼ぶ案は、外部 API、メッセージ、path 規則が結合し、未導入時の分岐を各コマンドに重複させるため採らない。独自 SSH/SFTP client の案は、要件 AC4 と既存 content API の CCSID/cleanup 責務に反するため採らない。

## D4: 色属性を保持するため同期は独自の SSH/SFTP 経路へ切り替える

- 状況: 利用者は既存の RPG 等のソースメンバーに埋め込まれた SEU の色属性を維持し、VS Code 上では色を識別できる可視記号（例: 赤属性の `Ŕ`）として編集したい。Code for IBM i は SEU 色をサポート対象外としており、既存の content API に文字列を無変換で渡す方針では、色属性の保持を保証できない。
- 決定: Code for IBM i の接続 profile、公開・非公開 API、内部 SFTP client は利用しない。本拡張の設定に接続先の非機密情報を保持し、独自の SSH/SFTP 経路でメンバーを送受信する。可視記号とホストの属性バイトの対応・CCSID・一時 IFS 経路の正確な扱いは research で確定する。
- 理由: 色属性を操作可能な VS Code 上の記法にしつつ、送受信時の正確な可逆変換を本拡張が支配するため。Code for IBM i の非公開接続情報を借りると、公開 API の契約外となり更新時に破綻する。
- 影響: 以前の D1 と D3 にある Code for IBM i adapter / content API の判断は廃止する。接続設定と認証情報の安全な保管、SSH/SFTP のエラー処理、実機での raw byte 往復検証がこの work の対象になる。

## D5: source PF の CCSID は設定せず `DBFCCSID(*FILE)` を使う

- 状況: source PF の CCSID は環境・ファイルごとに異なり、利用者設定に複製すると値のずれによる文字化けを生む。実機調査では CCSID 5035 で色属性を含む UTF-8 往復を確認した。
- 決定: `CPYTOSTMF` と `CPYFRMSTMF` に `STMFCCSID(1208) DBFCCSID(*FILE)` を指定する。CCSID 65535 で IBM i が変換を拒否した場合は更新せず、理由と修正操作を通知する。
- 理由・代替案: IBM 原典は `*FILE` が database/source file CCSID を使うと規定する。設定 `sourceCcsid` を追加する案は source PF との二重管理になり、更新時に誤設定を検知できないため退ける。
- 影響: 同期専用 settings に CCSID は含めない。DBCS と色属性の変換は IBM i の file CCSID を正とし、UTF-8 wire から可視マーカーへの変換だけを拡張側が担う。

## D6: 初期 UI は7基底色を可視マーカー化し、修飾属性は無変換で通過させる

- 状況: 実機で確認した基底色は 7 種であり、利用者が指定した `Ŕ` のように色名を読める一文字を割り当てられる。一方、反転・下線等を組み合わせた 25 以上の属性値を、一文字で意味が分かる文字へ一意に割り当てるには別の利用者記法の合意が要る。
- 決定: green/white/red/turquoise/yellow/pink/blue の7基底値だけを可視マーカー化・装飾・キーボード入力の対象とする。その他の wire 制御文字は変換せず、ダウンロード→無変更アップロードで通過させる。削除・既知の色への丸めはしない。
- 理由・代替案: 全属性を private-use 文字へ割り当てる案は可逆だが「Red の R が見える」という目的を満たさない。未知属性を拒否する案は既存メンバーを読めなくする。まず実用上の色記法を実現し、修飾属性の可視記法は後続要件で追加する。
- 影響: AC11 のサポート対象は research で確定した7基底色である。修飾属性は保持されるが VS Code 上での色装飾・新規入力の対象外であり、テストで無変換通過を固定する。

## D7: アップロード時のファイル名区切り文字は `_`（アンダースコア）ではなく `-`（ハイフン）にする

- 状況: US4（AC12〜AC18）でファイル名から `<メンバー名><区切り><テキスト記述>.<拡張子>` を抽出する際、ユーザーの初回要望は区切り文字にアンダースコアを想定していた。しかし `IBM_I_OBJECT_NAME`（`vscode-extension/src/sync/memberTarget.ts:8`）が示すとおり、IBM i のオブジェクト名（メンバー名を含む）はアンダースコアを合法文字として許容する。そのため `_` を区切りにすると、`MY_PGM.rpg`（7文字、今日も有効なメンバー名として解決できる）のような既存の命名と衝突し、**メンバー名 `MY` + テキスト記述 `PGM` へ黙って解釈が変わり、意図しない別メンバーへ送信先が変わる**リスクがある。
- 決定: 区切り文字を `-`（ハイフン）にする。`IBM_I_OBJECT_NAME` の許容文字集合（半角英数字・`$` `#` `@` `_`）にハイフンは含まれないため、メンバー名の内部にハイフンが現れることは原理的に無い。よって「まず全体を有効なメンバー名として検証し、無効な場合だけ分割する」といったフォールバック分岐も不要になり、常に最初の `-` で単純に分割してよい。
- 理由・代替案: (a) 「全体を先にメンバー名として検証し、有効ならそれを採用、無効な場合だけ最初の `_` で分割」という後方互換フォールバック案も検討したが、分岐が増えるうえ、同じファイル名でもメンバー名の桁数次第で意味が変わる（`AB_CD.rpg` は分割されないが `ABCDEFGHIJ_X.rpg` は分割される）という利用者から見て不可解な挙動になるため採らない。(b) `_` のまま常に分割する案は、既存のアンダースコア入りメンバー名の解決結果を静かに変えてしまうため採らない。
- 影響: `requirements.md` の US4・機能要件・AC12・AC13 の記述とサンプルファイル名を `-` 区切りへ修正した（元は `_` 区切りで記載していた）。design のファイル名解析ロジックは常に「最初の `-` で分割し、無ければ全体をメンバー名とする」の単純な規則でよい。

## D8: SRCTYPE は拡張子ごとの特例テーブルを持たず、一様に大文字化する

- 状況: research.md F11 で、対象拡張子（`TARGET_EXTENSIONS`）の大部分は大文字化が実務の SRCTYPE 慣行と一致すると確認できたが、`.dds`（AGENTS.md に「`.dds` と名付ける環境への保険」と明記された非主形の拡張子）については実世界の慣行を示す一次資料が見つからなかった。
- 決定: 特例を設けず、`TARGET_EXTENSIONS` の全拡張子（`.dds`/`.mnudds` を含む）に同一の規則「拡張子を大文字化した文字列を SRCTYPE とする」を適用する。
- 理由・代替案: (a) `.dds` だけ SRCTYPE 反映を対象外にする案は、他の拡張子と挙動が分かれ利用者から見て理由の説明しにくい特例になるため採らない。(b) `.dds` に固定の代替値（例: 汎用 `DDS`）を割り当てる案は、結局「大文字化した結果」と同じ値になるため、特例として持つ意味が無い。(c) すべての `TARGET_EXTENSIONS` を大文字化した結果は、SRCTYPE の規則（10文字以内・英字始まり・残りは英数字/下線）を機械的に満たすことを確認済み（design.md「ドメイン固有の考慮」）。SRCTYPE パラメーターは実機で列挙値に制限されない欄であり、規則さえ満たせば任意の文字列を書けるため、一様な規則を採っても実機で拒否される懸念は無い。
- 影響: `deriveSourceType` は特例分岐を持たない1行の純粋関数になる。`.dds` を使う利用者は SRCTYPE `DDS` を受け取る。実務での慣行と異なる場合は、利用実績が増えてから特例を追加する。

## D9: T11（実機検証）は coding 工程では消化せず未チェックのまま test 工程以降へ送る

- 状況: T8〜T10 の実装・unit test（fake ssh client）は完了した。T11 は全角テキスト記述の `CHGPFM ... TEXT('...')` 往復、宛先メンバー未存在時の `CPYFRMSTMF` 自動作成、宛先ライブラリー／ソース物理ファイル未存在時の失敗を実機で確認するタスクである。現セッションは `PUB400_USER`/`PUB400_PASSWORD` が未設定、`sshpass` 未導入、`ts5250` MCP も接続タイムアウトで、IBM i 実機に到達する手段が無い。
- 決定: T11 は本 coding 工程では実施せず、`tasks.md` 上で未チェックのまま test 工程（またはそれ以降、実機に到達できるセッション）へ送る。実施したふりをした記録や、未検証のまま実機確認済みと書くことはしない。
- 理由・代替案: 実機に接続できない状態で「確認した」と記録すると、AGENTS.md の検証規約（実機で確かめるまで使わないこと）に反し、後続工程が誤った前提で進む。ローカルの fake ssh client によるコマンド列・エスケープの unit test（T9）は「送信するコマンド文字列が正しいこと」までは担保するが、「IBM i が実際にそれを正しく解釈すること」（特に全角文字の往復）は担保しない。両者を区別して記録する。
- 影響: `aidev-30-tasks` 手順6の運用に従い、T11 は完了条件から外さず tasks.md に残したまま未チェックで coding を終える。test 工程で実機に到達できるセッションがあれば、そこで T11 を消化する。到達できないまま test/deliver まで進める場合は、test-result.md に「未検証」として明記し、成功扱いにしない。

## D10: `CHGPFM` の `TEXT('...')` に remote shell 向けのエスケープを追加する（review ラウンド3 の指摘対応）

- 状況: review ラウンド3 で、`escapeClStringLiteral`（CL 文字列リテラルのアポストロフィ二重化）だけでは `system "CHGPFM ... TEXT('...')"` 全体を包む**外側の二重引用符**を保護できないという指摘が出た。`client.exec()` のコマンド文字列は SSH サーバー側でログイン shell に `shell -c '<command>'` として実行させるため、外側の二重引用符は remote shell が解釈し、`\` `"` `$` `` ` `` を特殊文字として扱う。research.md F12 では「少なくとも2層のエスケープが必要」と正しく指摘していたが、design.md・当初の実装では CL 単引用符の層しかエスケープしておらず、`textDescription` に `"` や `$` を含むファイル名でアップロードすると、意図しないコマンドが remote shell に注入され得た。
- 決定: `escapeForRemoteShellDoubleQuoted`（`\` `"` `$` `` ` `` を `\` で前置）を新設し、`escapeClStringLiteral` の**後に**適用してから `TEXT('...')` を組み立てる（内側の CL エスケープを先に行い、その結果を外側の shell エスケープで包む。評価順序は逆——remote shell が先に自分のエスケープを剥がし、その結果を CL パーサーがアポストロフィ二重化として解釈する）。
- 理由・代替案: 対象4文字（`\` `"` `$` `` ` ``）は POSIX 系 shell の二重引用符コンテキストで特殊な意味を持つ標準的な集合。`library`/`sourceFile`/`member`/`sourceType` は `IBM_I_OBJECT_NAME`/`SOURCE_TYPE` 正規表現で英数字・`$` `#` `@` `_` のみに制限されており、`$` は含み得るが英大文字直後の `$`（末尾のみ許容）で shell 展開の対象になる `${...}` や `$(...)` の形を作れないため、この4値にはエスケープを適用していない（`$` 単体は POSIX shell の変数展開の開始文字だが、後続文字が無い・英数字でないと変数参照にならない。ただし将来 `library`/`sourceFile` にも `$` の位置によって展開の懸念が生じ得るため、疑わしい場合は同じ関数を再利用できるようにしている）。
- 影響: `vscode-extension/src/sync/ibmiSourceTransport.ts` の `buildChangeAttributesCommand` を修正。回帰テスト（remote shell 特殊文字のエスケープ、修正前に戻すと fail することを確認済み）を `vscode-extension/test/unit/memberSync.test.ts` に追加。test-result.md・review.md に反映。
