# 要件: DDS 定位置欄の値集合を実機で網羅し、`restricted` を広げる

## 背景 / 課題

DDS プロンプター定義の定位置欄（1 文字の選択欄）は 8 つあるが、
**`restricted: true` が立っているのは表示装置 38 桁の 1 件だけ**で、残り 7 欄は
`restricted: false`＝「列挙した値は候補にすぎない」扱いのままになっている。

| 種別 | 桁 | 値 | 状態 |
|---|---|---|---|
| 物理/論理 | 17 | `_RKJSO` | false |
| 物理/論理 | 35 | `PSBFAHLTZ5JEOG` | false |
| 物理/論理 | 38 | `_BIN` | false |
| 表示装置 | 17 | `_RH` | false |
| 表示装置 | 35 | `_XANSYWIDMFLTZJEOG` | false |
| 表示装置 | 38 | `_OIBHMP` | **true**（済） |
| 印刷装置 | 17 | `_R` | false |
| 印刷装置 | 35 | `SAFLTZ` | false |

`false` の間は 2 つのことが起きない。**lint（`restricted-value`、既定 ON）が
その欄を一切見ない**ので、実機が弾く値がソースに入っていても指摘されない。
**プロンプターの入力欄も錠前にならない**ので、無効な値を打てる。

一方で、**確かめずに `true` にすると正しいソースを弾く**。前作業で実際に、
印刷装置 35 桁は原典に無い `G` / `O` を実機が受けることが分かっている。
さらに `true` の欄は WebView が `buildSelect` を使い（`ui.ts:343-352`）、
`select.value = field.value` は**一覧に無い値を黙って落とす**——完全性の
裏づけが無いまま `true` にすると、既存ソースの値が確定操作で消える。

前作業（`20260829-dds-restricted-enable`）で**網羅の手法は確立済み**
（1 文字の欄は空間が 37 通りなので全部試せば漏れの無さまで決まる。
`verify/probe-exhaustive.mjs` / `probe-columns.mjs`）。残り 7 欄は
手法が無いのではなく、**まだ流していない**か**流したが結果を採れなかった**。

出所: `.aidev/backlog/workflow.md`「残りの DDS 欄を実機で確かめて `restricted` を広げる」。

## 目的 / ゴール

**DDS の定位置欄について、実機が受ける値の集合が欄ごとに判明していて、
一致した欄では無効な値が lint とプロンプターの両方で止まる状態。**
一致しなかった欄は、**なぜ一致しないかが根拠つきで記録されていて、
候補つき自由入力のまま安全に据え置かれている**状態。

紐づく charter ゴール: 「プロンプター定義の拡充」および DDS の柱の
「原典に記述が無い挙動は**実機（IBM i）で確かめ**、確認手順を成果物に残す」。

## ユーザーストーリー

- US1: **DDS を書く開発者**として、定位置欄に実機が弾く値を書いたらその場で
  指摘してほしい。なぜなら、いまは**コンパイルするまで気付けず**、
  桁の問題と誤診して切り分けに時間を失うから。（受け入れ: AC4, AC5, AC7）
- US2: **既存の DDS を保守する開発者**として、プロンプターで欄を開いて確定しても
  **元の値が消えないでほしい**。なぜなら、実機が受ける値を定義が知らないだけで
  黙って書き換えられると、動いていたソースが壊れるから。（受け入れ: AC3, AC6, AC8）
- US3: **この定義を後から広げる開発者**として、**採らなかった欄の理由**を
  残してほしい。なぜなら、理由が無いと同じ検証を繰り返すか、
  逆に「未確認」を「確認済み」と取り違えて誤って `true` にするから。（受け入れ: AC2, AC9）

## スコープ

### 対象

- **物理/論理 35・38 桁**: 雛形を直すところから（前回は対照 `A` が落ちた）。
- **表示装置 35 桁**: 一括の読み取りが当てにならなかったので、単独で流す。
- **印刷装置 35 桁**: 網羅したうえで、原典に無い `G` / `O` を
  **`ORIGIN_ERRATA` で補うかを判断**する。
- **17 桁（仕様のタイプ）× 3 種別**: 1 文字の網羅がそのままでは使えない
  （値を変えると行の種類が変わる）。**別の手法を試み、確立できたら実施する。**
- 一致した欄の `PROVEN_COMPLETE` 追加と定義 JSON の再生成（PF/DSPF/PRTF × ja/en）。
- 前作業と同じ**検証スクリプトと結果の記録**（`verify/`）。

### 対象外

- **`restricted` 以外の属性**（`numericOnly` / `maxLength` 等）の見直し。
- **2 文字以上の欄**。網羅の空間が 37 通りに収まらず、手法が別になる。
- **RPG / CL の定義**。今回は DDS の定位置欄だけ。
- **原典の取得しなおし**（`docs/origin/dds/` の HTML は既存のものを使う）。
- lint 規則そのものの変更（`restrictedValue.ts` は既にあり、既定 ON）。

## 機能要件

- 欄ごとに全 37 通り（ブランク ＋ A-Z ＋ 0-9）を実機に判定させ、
  **「値として無効」と「認識されたが文脈違い」をメッセージ番号で読み分ける**。
- **対照を必ず置く**。原典にあって通ると分かっている値と、原典に無く弾かれると
  分かっている値の両方を同じ流しに混ぜ、対照が期待どおりでない結果は採らない。
- 実機が受ける集合と定義の集合が**完全一致した欄だけ** `PROVEN_COMPLETE` に入れる。
- 一致しなかった欄は `false` のまま据え置き、**理由を生成スクリプトの表に記録**する。
- 原典側を補う判断をした場合は `ORIGIN_ERRATA` に**根拠を添えて**書く。
- 定義 JSON は手で直さず、**生成スクリプト（`generate-dds-prompter.mjs`）を直して再生成**する。

## 非機能要件 / 制約

- 実機は共用機。**ssh / 接続を細かく張らない**。1 欄あたり 1 回の流しにまとめ、
  単独判定が要る場合だけ回数を増やす。
- 実機に作ったオブジェクト・IFS ファイル・スプールは**すべて片付ける**（残数 0）。
- 定義スキーマは `vscode-extension/src/prompter/types.ts` に準拠する。
- 既存挙動を壊さない（後方互換）。
- 検証スクリプトは `verify/` に残し、**同じ検証を再実行できる**形にする。

## 相互作用の受け入れ基準

`restricted` を `true` にすると、プロンプターの入力欄が
**候補つき自由入力（`buildOpenChoice`）から錠前の `<select>`（`buildSelect`）へ切り替わる**。
利用者が操作する部品が変わるため、次を確認する。

- [ ] AC-I1 開く / 閉じる: `true` にした欄を F4 で開くと `<select>` が出る。
      閉じても（取り消しても）ソースの値は変わらない。
- [ ] AC-I2 確定 / 取り消し: **何も触らずに確定したとき、元の値がそのまま残る**。
      `select.value = field.value` は一覧に無い値を黙って落とすため、
      **完全性が保証できた欄以外では `true` にしない**ことでこれを担保する。
- [ ] AC-I3 キーボードだけで完結する: 開く → 値を選ぶ → 確定 → ソースへ戻る、が
      マウス無しで通る（`<select>` の標準操作で足りることを確認する）。
- [ ] AC-I4 フォーカスの行き先: 開いた直後にカーソル行の欄へフォーカスが移り、
      閉じるとエディターの元の位置へ戻る（既存の挙動から変わらない）。
- [ ] AC-I5 既存の操作を妨げない: `false` のまま据え置いた欄は
      **これまでどおり自由入力**で、一覧に無い値も打てる（後退させない）。

## 未確定事項 / 確認したいこと

- **物理/論理の雛形がなぜ落ちたか**。前回は対照 `A` が通らなかった。
  `CRTPF` の最小の形（位置欄なし・キーなし）が正しいか、
  レコード長やソース・タイプの与え方が違うのかを切り分ける必要がある。→ research で解消。
- **17 桁の手法**。値ごとに構造上の前提が違う（`K` はキー・`J` は結合仕様）ため、
  1 つの雛形では有効な値まで落ちる。**「17 桁の値が無効」を意味するメッセージ番号**を
  特定できれば、構造由来の失敗と読み分けられる可能性がある。→ research で確かめる。
- **印刷装置 35 桁の `G` / `O` を原典 errata として補うか**。実機が受けることは
  前回の単独確認で分かっている。補えば `true` にできるが、
  **原典の不足を定義側で埋める判断**なので根拠の書き方を決める必要がある。→ spec で決める。
- 表示装置 35 桁を単独で 37 回流すときの**実機負荷**。1 回にまとめられないか、
  まとめると読み取りが当てにならないのか。→ research で確かめる。
