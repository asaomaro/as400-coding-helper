# 要件: AI にテストを書かせる手順を確立する

## 背景 / 課題

設計書 4.2「AI にテストを書かせる場合の方針」は**方針**を述べているが、
**実行手順になっていない**。受け入れ条件 4 つのうち道具が要るものは片付いた。

| # | 条件 | 状態 |
|---|---|---|
| 1 | 新規は設計書をオラクルにする | **手順が無い** |
| 2 | 既存は特性化と明記させる | **手順が無い** |
| 3 | ミューテーションで検出力を検品 | やり方は実証済み。手順が無い |
| 4 | `ORDER(*REVERSE)` で独立性を検品 | **道具になった**（`--check-independence`） |

方針だけでは実行されない。**手順と、機械で検査できる形**が要る。

本セッションで 1 と 3 の失敗を実際に踏んでいる。

- **1**: `assertEqual(105 : addTax(100 : 0.055))` の期待値 105 に**根拠が無かった**。
  落ちたとき**テストを実装に合わせて直した**（実装が正しい保証は無いのに）。
- **3**: 旧 `iEqual` は型で丸めるため**検出力が落ちていた**（105 と 105.50 を区別できない）。

## 目的 / ゴール

**AI にテストを書かせるとき、期待値の出所が追え、検出力が検品された状態**で
成果物が出てくること。人が毎回思い出さなくても、手順を踏めばそうなる。

紐づく charter ゴール: 主要 3 本柱を支える検証基盤（`品質基準`「テスト通過」）。

## ユーザーストーリー

- **US1**: AI にテストを書かせる者として、**踏むべき順序と検品**を 1 か所で見たい。
  なぜなら、方針を読んで毎回自分で手順に翻訳するのは続かないから。（AC1, AC2）
- **US2**: レビューする者として、**期待値の出所が成果物に書いてある**状態にしたい。
  なぜなら、コードを読んでも「どこから来た値か」は分からないから。（AC3）
- **US3**: 手順を回す AI として、**検品が機械的**であってほしい。
  なぜなら、人の判断が要る検品は省かれるから。（AC4）

## スコープ

### 対象
- 手順の文書化（書く前 → 書く → 検品する、の順序）。
- **期待値の出所を成果物に残す書式**（機械で検査できる形）。
- 3 つの検品（コンパイル・独立性・検出力）の回し方。
- 「網羅」の数え方（設計書の条項に対して）。

### 対象外
- 検品の完全自動化（ミューテーションの変異選びは人／AI の判断）。
- カバレッジ計測（設計書が「参考値に留める」としている）。
- RPG III 向けの手順（サブプロシージャーが無く RPGUnit を書けない）。

## 非機能要件 / 制約

- **同じ内容を 2 か所に置かない**。手順は skill 1 か所、設計書は方針のまま。
- 例は**実機で通したもの**だけを載せる。

## 完了条件 (受け入れ基準)

- [ ] **AC1**: 受け入れ条件 4 つすべてが手順の中に位置づけられている。
- [ ] **AC2**: 「書く前 → 書く → 検品する」の順序が示され、各段でやることが具体的。
- [ ] **AC3**: 期待値の出所を残す書式が決まっており、**機械で検査できる**形になっている。
- [ ] **AC4**: 3 つの検品が**実際のコマンド**で書かれている（概念の説明で終わらない）。
- [ ] **AC5**: 設計書 4.2 から手順の場所が辿れる（到達可能）。
- [ ] **AC6**: 例は本セッションで実機に通したものだけ。
