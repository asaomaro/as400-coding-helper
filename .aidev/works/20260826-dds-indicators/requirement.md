# 要件: 条件標識の解決と標識パネル（DDS デザイナ）

## 背景 / 課題

DSPF の項目は**オプション標識（01-99）で表示が条件付けられる**。原典（`表示装置ファイルの条件付け (7 - 16 桁目)`）:

> ユーザー・プログラムでは、オプション標識をオン (16 進数 F1) またはオフ (16 進数 F0) にセットすることにより、
> フィールドまたはキーワードを選択することができます。

いまの DDS デザイナは、条件付け欄を**読んではいる**（`readConditioning` が `Conditioning` を返す）が、
**「どの標識が立っているとどう見えるか」を決める手段が無い**。結果として:

- キャンバスは**条件を無視して全部を重ねて描く**。`01` のときだけ出る項目と `N01` のときだけ出る項目が
  **同じ桁に並んで見える**ため、実機での見え方が画面から読めない。
- そのため**条件付きの重なりが見つからない**。`resolveDspfLayout` の重なり検出は
  `isMutuallyExclusive` が「片方でも条件が付いていれば排他」と保守的に倒しているので、
  **条件付き項目どうしの重なりは一切報告されない**（誤検出を避けるための意図的な判断）。
  結果、**同じ標識が立ったときに本当に重なる**組み合わせも黙って通る。
- 確定デザイン C1 の左ペイン下段（`条件標識` カード）が**空白のまま**である。

紐づく charter ゴール: **DDS（DSPF/PRTF）の視覚的な確認と編集**を第 4 の柱として加える。

## 目的 / ゴール

**標識の組み合わせを指定すると、その組み合わせでの実機の見え方がキャンバスに出ている状態**。
そのとき初めて重なる項目は、**その状態でだけ**指摘として出ている。

指定していない標識があっても破綻せず、**何も指定していなければ今までと同じ見え方**である。

## ユーザーストーリー

- US1: DSPF を直す開発者として、**標識をオン/オフしてキャンバスの変化を見たい**。
  なぜなら、条件付きの項目が重なって描かれた画面からは**実機でどう見えるかが読めず**、
  いまは実機で表示して初めて分かるから。（受け入れ: AC1, AC3, AC4）
- US2: DSPF を直す開発者として、**その項目にどんな条件が付いているかをプロパティで読みたい**。
  なぜなら、条件は**項目の行より前の行**に書かれることがあり、ソースを目で追わないと分からないから。
  （受け入れ: AC5）
- US3: DSPF を直す開発者として、**ファイル中で使われている標識の一覧**を見たい。
  なぜなら、`01` を立てたいのに実際には `N01` で条件付けられている、といった取り違えを
  **一覧が無いと総当たりで探すことになる**から。（受け入れ: AC2, AC3）
- US4: DSPF を直す開発者として、**その標識の組み合わせで重なる項目**を知りたい。
  なぜなら、条件付きの重なりは今の検出では**原理的に報告されない**（保守的に倒してある）から。
  （受け入れ: AC6）

## スコープ

### 対象

- core: 条件付けの**解決**（標識の状態 → その項目が出るか）と、ファイル中の標識の**列挙**。
- 描画モデル: 標識の状態を受け取り、条件が成立しない項目を**描かない**。
- UI: 左ペイン下段の `条件標識` カード（一覧・3 値の切替・全解除）。
- UI: プロパティに**その項目の条件**を読み取り専用で出す。
- その標識の状態での**重なり**を、状態を指定しているときだけ指摘に出す。

### 対象外

- **条件標識の編集**（付け外し・OR 条件の追加）。**この work では読むだけ**。
  解決が無いと編集した結果を確かめられないので、解決を先に置く（backlog に残す）。
- `isMutuallyExclusive`（ファイル診断側の重なり判定）の**厳密化**。
  静的に厳密化すると `01` と `02` の重なりを報告することになり、
  原典が正当と認める使い方（プログラムが排他を保証する）に誤検出が出る。
  **状態を指定したときだけ**見る、という形に留める。
- 標識に説明（`CA03 応答標識` 等）を付ける機能。ソースに書かれていない情報なので出所が無い。
- 標識の状態の永続化（再起動をまたいで覚える）。

## 機能要件

- 条件付けを**論理式として解決**する。原典の構造に従う——
  AND で結んだ標識が 1 つの条件、条件どうしを OR で結ぶ（最大 9 条件 × 9 標識）。
- 標識の状態は **3 値**（`オン` / `オフ` / `未設定`）。未設定を含む条件は
  **成立とも不成立とも決めない**（`unknown`）。
- `unknown` の項目は**描く**（今までと同じ）。`不成立` の項目だけ描かない。
- 標識の一覧は**ソースに現れた標識だけ**を、番号順に出す。使用箇所の件数を添える。
- 条件が成立しなかった項目は、**様式ツリーには残す**（理由付き）。キャンバスから消えた項目に
  ツリーからも手が届かなくなると、戻す手段がテキストエディタしか無くなる。

## 非機能要件 / 制約

- **既存挙動を壊さない**: 標識を 1 つも設定していない状態＝**今までと同じ描画**（後方互換）。
- core は `vscode` を import しない（単独起動でも同じものが動く）。
- 判定の根拠は**原典**（`docs/origin/dds/FIELD-DSPF-pos716.html`）を正とする。
- 標識の状態は**ソースを書き換えない**（表示だけ。ルーラー / SOSI と同じ考え方）。

## 完了条件 (受け入れ基準)

- [ ] AC1: 標識の状態（3 値）を与えると、各項目が `出る` / `出ない` / `決まらない` に解決される。
      AND / OR の組み立ては原典どおり（`O` が新しい条件を開始し、`A`・ブランクは AND の継続）。
- [ ] AC2: ソース中で使われている標識を、番号順・使用箇所件数つきで列挙できる。
- [ ] AC3: 左ペインの `条件標識` カードで、各標識を `オン` / `オフ` / `未設定` に切り替えられ、
      切り替えるとキャンバスが即座に変わる。`すべて未設定` に戻せる。
- [ ] AC4: 条件が成立しない項目はキャンバスに描かれず、様式ツリーには `条件で非表示` として残る。
- [ ] AC5: プロパティに、選択中の項目の条件が読める形（例 `01 かつ N02、または 03`）で出る。
      条件が無ければ `なし`。
- [ ] AC6: 標識を 1 つ以上設定しているとき、**その状態で同時に表示される**項目どうしの重なりが
      指摘に出る。何も設定していなければ出ない（＝既存の指摘だけ）。
- [ ] AC7: 標識を 1 つも設定していない状態の描画が、この変更の前と一致する。
- [ ] AC8: 標識の切替でソースは変わらない（編集イベントを送らない）。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開く / 閉じる: `条件標識` カードは**常に開いている**（開閉しない）。標識が 1 つも
      使われていないファイルでは、カード自体を出さずに「使われていません」と出す。
- [ ] AC-I2 確定 / 取り消し: 切替は**即時反映**（確定操作は無い）。`すべて未設定` が取り消しにあたる。
- [ ] AC-I3 キーボードだけで完結するか: 各標識の切替は `Tab` で到達し、**矢印キーで値を選べる**。
      （当初は「`Enter`/`Space` で巡回」と書いたが、research F7 で
      **巡回ボタンはどの流儀にも当たらない**（現在値と次の値が読めない）と分かったため、
      APG のラジオグループに改めた。）
- [ ] AC-I4 フォーカスの行き先: 切替後もその標識のボタンにフォーカスが残る
      （再描画でフォーカスを失うと、連続して切り替えられない）。
- [ ] AC-I5 既存の操作を妨げないか: カード上のキーは**キャンバスの矢印移動に漏らさない**
      （既存の `isTypingTarget` と同じ考え方でボタン上のキーを止める）。
