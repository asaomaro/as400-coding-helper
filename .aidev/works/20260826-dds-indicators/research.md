# 調査: 条件標識の解決と標識パネル

## 調査の問い

- Q1: 原典は条件付けの論理構造をどう定めているか（AND / OR の組み立て、上限）。
- Q2: いまの `readConditioning` は、その構造を**復元できる形**で保持しているか。
- Q3: 標識はどの行に現れるか（項目の行だけか）。列挙はどこから作るべきか。
- Q4: 描画モデルは誰が組み立てているか。標識の状態は**どちら側**に置くべきか。
- Q5: 3 値（オン / オフ / 未設定）の切替 UI に、確立したパターンはあるか。
- Q6: 「描かない」と「淡く残す」のどちらを既定にすべきか（requirement の未確定事項）。

## 判明した事実

### F1: 条件は「AND で結んだ標識の組」を「OR で結んだ」もの（DNF）

原典（`docs/origin/dds/FIELD-DSPF-pos716.html` = `表示装置ファイルの条件付け (7 - 16 桁目)`）:

> 2 - 9 個の標識を AND により結び付けて 1 つの条件にすることができます。この場合、AND 関係にある
> 標識すべてが効力を持っていなければ (つまり、すべての標識がオンまたはオフを満たしていなければ)、
> フィールドまたはキーワードは選択されません。
> **AND 条件は、N が指定されていればオフに、N が指定されていなければオンに設定されます。**

> 1 つのフィールドまたはキーワードについて**最大 9 つの条件**を指定することができ、
> 1 つの条件について**最大 9 つの標識**を指定することができます。
> したがって、1 つのフィールドまたはキーワードについて、最大 81 個の標識を指定することができます。

> また、1 つのフィールドまたはキーワードについていくつかの条件を指定し、
> **そのうちのいずれか 1 つが満たされれば**、そのフィールドまたはキーワードが選択される
> ようにすることもできます。これは **OR 関係**と呼ばれます。

行の組み立て:

> **7 桁目 (AND)** … AND 条件をつくるために 4 つ以上の標識が必要な場合には、標識を次の行以降に
> 指定します。AND 条件の継続を示すためには、2 行目以降の 7 桁目に A を指定してもよいのですが、
> **この A はデフォルト**なので、7 桁目をブランクのままにしておいても差し支えありません。
> **7 桁目 (OR)** … OR で結ばれる複数の条件を指定する場合には、各条件をそれぞれ新しい行から
> 書き始め、**最初の条件以外のすべての条件については、7 桁目に O を指定**しなければなりません。
> **最初の条件に O を指定した場合には、警告メッセージが出て、この桁はブランクとして処理されます。**

> **8 桁目、11 桁目、14 桁目 (NOT)** … ある条件を満たすために、標識がオンではなくオフである
> ことが必要な場合には、その標識の直前の桁 (8 桁目、11 桁目、または 14 桁目) に N を指定します。

> フィールドまたはキーワードは、**最後の (または唯一の) 標識の組み合わせを指定した行と同じ行**に
> 指定しなければなりません。

つまり、**行 → 条件（OR グループ）への畳み込み**は次のとおり:

- 1 行目は必ず新しい条件を開始する（`O` が書かれていてもブランク扱い）。
- 2 行目以降、7 桁目が `O` なら**新しい条件を開始**、`A` またはブランクなら**直前の条件に AND で足す**。

### F2: `readConditioning` は行単位の `join` を保っており、畳み込みは復元できる

`src/core/dds/ddsConditioning.ts:56` `readConditioning` は `clauses: { join: "A"|"O", terms }[]` を
**行の順序どおり**に返す（`join` は 7 桁目、ブランクは `"A"`。`ddsConditioning.ts:64`）。
F1 の畳み込み規則をそのまま適用でき、**構造は失われていない**。解決関数は同じファイルに足せばよい。

なお `Conditioning` は `none` / `indicators` / `screen-size` の 3 種で、
**画面サイズ条件名が付いていれば標識より優先して返す**（`ddsConditioning.ts:92`）。
画面サイズの不一致は既に `resolveDspfLayout` が落としている（`dspfLayout.ts:236`）ので、
解決関数から見た `screen-size` は**常に成立**として扱ってよい。

### F3: 標識は「項目の行」だけに現れるのではない（列挙は生の行から作る）

`toLogicalUnits`（`src/core/dds/ddsLogicalUnits.ts:137`）は、
**キーワード欄が空で条件付けだけの行**を次の単位の `conditioningLines` に前置きする（同 176-179 行）。
一方で**キーワードだけの行**（`DSPATR(RI)` など）は直前の単位の `keywords` に連結され、
**その行の条件付け欄は捨てられる**（同 186-192 行）。

原典は条件が付く対象を「フィールド**または**キーワード」としているので、
`30 DSPATR(RI)` のような**キーワードだけを条件付ける標識は `conditioningLines` に入らない**。

- **項目が出るか**の判定には影響しない（項目の表示を決めるのは項目自身の条件だけ）。
- **標識の列挙**（AC2）には影響する。単位から集めると `30` を取りこぼす。
  → 列挙は **`toLogicalUnits` を通さず、注記行・空行を除く全行の条件付け欄**から作る。

### F4: 描画モデルはホストが組み立てて UI に送る

`buildDspfRenderModel(lines)` の呼び出しは**ホスト側だけ**——
`src/dds/editorProvider.ts:262`（VSCode）と `dev/standalone.ts:129`（単独起動）。
UI（`src/dds/webview/ui.ts`）は core から**型しか import していない**（`ui.ts:1-3`）。
モデルは `postMessage`（構造化複製）で渡るので、載せる値は**素のオブジェクト / 配列**に限られる。

`fromLayout` は export されているが**外部の呼び出し元は無い**（`dspfRenderModel.ts` 内のみ）。

したがって標識の状態を**ホストに持たせると往復が要る**（`setIndicators` → 再構築 → 返送）。
直前の work（`20260826-dds-display-toggles`）で確立した形は逆で、
**表示の状態は UI が持ち、ホストへ送らない**（PR #111）。標識の状態も**ソースを書き換えない表示**なので、
同じ側に置くのが一貫する。

### F5: `hidden` の仕組みは既にあり、そのまま流用できる

`OutlineItem.hidden`（`src/core/dds/dspfOutline.ts:42`）は
`no-position` / `invalid-position` / `not-displayed` の 3 値で、UI は `describeHidden`
（`ui.ts:1074`）で日本語にして様式ツリーに出している。**理由を 1 つ足すだけ**で
「キャンバスから消えたが一覧には残る」が実現できる（AC4）。

`dspfOutline.test.ts` に**ドリフト検査**がある（一覧の `hidden` と `layout.items` の食い違いを検出。
`dspfOutline.ts:143` のコメント）。標識の状態を与えない既定では両者が変わらないことが前提。

### F6: 重なり検出は「条件が付いていれば常に排他」に倒してある

`isMutuallyExclusive`（`ddsConditioning.ts:112`）は
**両方とも無条件のときだけ `false`**（＝重なりを報告する）を返す。理由も原典で裏付けてある:

> 1 つのレコード様式内で、フィールドを他のフィールドまたは属性文字とオーバーラップするように
> 定義することができます。ただし、このように相互にオーバーラップするフィールドのうち、
> **一時点で画面に表示されるのは 1 つだけ**です。（`位置 (39 - 44 桁目)`。`dspfLayout.ts:355` に引用）

つまり**条件付きの重なりは正当**であり、静的に厳密化すると `01` と `02` の重なりを
報告することになる（同時にオンになりうるので静的には排他でない）。実務の DSPF で誤検出が出る。

→ 状態を**明示した**ときだけ、その状態で同時に出る項目の重なりを見る、という形なら誤検出は出ない
（利用者が「この組み合わせ」と言い切っているため）。**既定（状態なし）では何も足さない。**

### F7: 3 値の切替は「ラジオグループ（分割ボタン）」が確立したパターン

- **WAI-ARIA APG の tri-state checkbox** は `aria-checked="mixed"` を持つが、`mixed` の意味は
  「部分的に選択されている」であって「**未設定**」ではない。今回の 3 値は排他な選択肢なので当たらない。
- **APG の Radio Group パターン**（`role="radiogroup"` ＋ `role="radio"` ＋ ローミング `tabindex`）が
  「3 つのうち 1 つ」に対する標準形。`Tab` でグループに入り、**矢印キーで値を選ぶ**。
  グループが増えても `Tab` の回数が増えないので、標識が並ぶ今回の形に合う。
- OS / 既存実装の例: macOS の分割コントロール（NSSegmentedControl）、VSCode 設定 UI の
  ドロップダウン（3 択以上）。**押すたびに巡回するボタン**は、現在値と次の値が読み取れないため
  スクリーンリーダーで状態が追えず、どの流儀にも当たらない。

→ **各標識 1 行 = `radiogroup`、中に `未設定` / `オン` / `オフ` の 3 つの `radio`**。
requirement の `AC-I3`（`Enter`/`Space` で巡回）は**この調査結果に合わせて矢印キーへ改める**
（spec で対応を書く）。

### F8: 「描かない」が原典に素直（Q6 の答え）

原典は条件が満たされないとき「フィールドまたはキーワードは**選択されません**」と書く。
実機では**出ない**のだから、キャンバスでも出さないのが見え方の再現になる。
淡く残すと「薄く出ている項目」という実機に無い状態を作ることになり、
`他様式を淡く`（別の意味で淡色を既に使っている）とも衝突する。
**消す。ただし様式ツリーには理由付きで残す**（F5）ので、手が届かなくなることはない。

## 影響範囲

- `src/core/dds/ddsConditioning.ts` — 解決・畳み込み・表示文字列・列挙を足す（既存 API は変えない）。
- `src/core/dds/dspfRenderModel.ts` — `RenderItem` に条件、`RenderModel` に標識一覧、
  状態を適用する関数を足す。
- `src/core/dds/dspfOutline.ts` — `HiddenReason` に 1 値足す（型のみ。生成側は変えない）。
- `src/dds/webview/ui.ts` / `ui.css` — 左ペインの標識カード、プロパティの条件行、`describeHidden`。
- `src/dds/webview/protocol.ts` — **変更しない**（状態はホストへ送らない）。
- `src/dds/editorProvider.ts` / `dev/standalone.ts` — **変更しない**（モデルの作り方は同じ）。

## 実現性 / リスク

- **後方互換**: 状態が空なら適用関数を**恒等**にすれば、既存の描画・診断・ドリフト検査に影響が出ない（AC7）。
- **リスク**: UI が core の実行時コードを import すると、WebView バンドルに core が入る。
  単独起動バンドルは既に core を含んでいる（`dev/standalone.ts`）ので新しい問題ではないが、
  **VSCode 用バンドルのサイズが増える**。`applyIndicators` は純関数なので影響は小さい。
- **リスク**: 再描画でフォーカスが飛ぶ（AC-I4）。プロパティ欄で既に踏んでいる罠で、
  `render()` が `focusedKey` を覚えて戻す仕組みがある（`ui.ts` の `renderProperties` 周辺）。同じ手を使う。

## 実装アンカー

- A1: 条件の解決を足す先（`src/core/dds/ddsConditioning.ts:97` `readConditioning` の直後）
  — `IndicatorTerm` / `IndicatorClause` / `Conditioning` が既にある。
- A2: 標識の列挙（`src/core/dds/ddsConditioning.ts` に新規）
  — 行の走査は `isDdsCommentLine` / `isDdsBlankLine`（`src/core/ddsLayout.ts`）と
  `conditioningAreaOf`（`ddsLogicalUnits.ts:133`）を使う。
- A3: `RenderItem` に条件を載せる（`src/core/dds/dspfRenderModel.ts:107` `toRenderItem`）
  — `DspfPlacedItem.conditioning` が既にある（`dspfLayout.ts:102`）ので詰め替えるだけ。
- A4: 標識一覧をモデルに載せる（`dspfRenderModel.ts:80` `buildDspfRenderModel` / `:85` `fromLayout`）
  — `fromLayout` は行を持たないので、引数を足すか呼び出し側で渡す。
- A5: 状態を適用する関数（`dspfRenderModel.ts` に新規）
  — 重なりの比較は `dspfLayout.ts:390` 付近の `overlaps(a.occupancy, b.occupancy)` と同じ形。
- A6: `HiddenReason`（`src/core/dds/dspfOutline.ts:42`）と `describeHidden`（`ui.ts:1074`）。
- A7: 左ペインの雛形（`ui.ts:1027` `template()` の `.dds-side.left`）と
  一覧描画（`ui.ts` `renderOutline`）。
- A8: 表示状態の持ち方（`ui.ts:92` 付近の `display` オブジェクトと `ui.ts:294` の再描画）
  — 標識の状態も同じ場所に置く。

## 実装時の注意

- **7 桁目は注記マーク（`*`）と AND/OR を兼ねる**。列挙で注記行を除かないと `*` を条件として読む。
- **`readConditioning` の既存の戻り値を変えない**。`dspfLayout` の重なり抑制
  （`isMutuallyExclusive`）が同じ値を使っており、ここを触ると**ファイル診断の挙動が変わる**。
- **`isMutuallyExclusive` を厳密化しない**（F6）。requirement のスコープ外に明記済み。
- 標識の番号は `01`-`99`。`readConditioning` は `padStart(2,"0")` で正規化している
  （`ddsConditioning.ts:84`）ので、状態の鍵も**必ず 2 桁**に揃える。
- 幅が読めない項目（`widthCols === undefined`）は重なりを判定できない。
  既存の `detectOverlaps` も `width === undefined` を飛ばしている（`dspfLayout.ts:369`）ので揃える。
- 既存の重なり指摘と**二重に出さない**。既存が出すのは「両方とも無条件」の組だけなので、
  状態つきの判定ではその組を飛ばす。

## spec への申し送り

- 状態は UI 側に持ち、`applyIndicators(model, states) → model` の**純関数 1 つ**を core に置く
  （F4）。プロトコルは変えない。
- `AC-I3` は「矢印キーで値を選ぶ」に読み替える（F7）。
- 未確定だった Q6 は「**描かない**（ツリーには理由付きで残す）」で確定（F8）。
