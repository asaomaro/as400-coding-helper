# 計画: 描画全体を実機のゴールデンと突き合わせる

## 実装方針
様式 → 採取 → 照合の順。**先に照合を書くと期待値を想像で書く**ことになるので、
実機の事実を採ってから照合を書く。ただし様式は「何を見たいか」から決める。

## 作業順序と依存関係
1. 検査用の様式（`RENDER1.dspf`）を生成して書き出す（依存: なし）
2. 採取スクリプトを書き、実機で採る（依存: 1）
3. 照合テストを書く（依存: 2）
4. **落ちることを確かめる**（桁を 1 つずらす／DBCS の数え方を戻す）（依存: 3）
5. 回帰（`npm test` / `npm run verify` / lint / e2e）

## リスク / 留意点
- 様式の桁ずれ。**生成して書き出す**こと（手で数えない）。
- `CRTSRCPF` の既定 CCSID 1027 は DBCS を黙って落とす → `CCSID(5035) IGCDTA(*YES)`。
- 5250 の装置は自動構成できない（`8940`）。既存の `ASA1`-`ASA4` / `ASAO3` / `ASAO4` を使う。
- 標識で隠す項目は、**画面に無いこと**を見る（`fields` にも `rows` にも現れない）。

## テスト方針
- 照合は `npm test`（実機に触らない）。
- **落ちることを確かめる**——モデル側で DBCS の桁を 1 つ減らすと検査 1 が落ちること。
- 採取スクリプトは work に残し、`node --env-file=... capture-render-golden.mjs` で採り直せる。
