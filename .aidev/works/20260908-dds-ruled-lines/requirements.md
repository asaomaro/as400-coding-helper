# 要件: 罫線を引けるようにする（DSPF / PRTF）

> **依存**: `20260908-dds-new-and-records`（様式が無いと罫線も置けない。deliver 済み・充足）。

## 背景 / 課題

DDS ビジュアルエディタはフィールド・定数・様式は視覚的に扱えるが、**罫線・枠は扱えない**。
罫線の実体は種別で異なり、状況も違う。

| | 罫線の実体 | 状態 |
|---|---|---|
| **DSPF** | `GRDLIN`（線）/ `GRDBOX`（枠）/ `GRDATR`（属性）/ `GRDCLR`（消去） | **原典を取得していない**（下記） |
| **PRTF** | `BOX`（長方形）/ `LINE`（縦横線）— レコード・レベル | 補完データにはあるが**描画モデルに載っていない**（`prtfLayout` が「SPACE/SKIP を無効にするキーワード」として名前を知っているだけ） |

利用者は帳票・画面の罫線をテキストエディタで手書きするしかなく、位置・長さを目視で数えて
書く必要がある——SEU 世代の作業がそのまま残っている状態。

### 先に塞ぐ穴: 原典の取得漏れ（DSPF の GRD 系）

DSPF の GRD 系 4 キーワードは、**キーワード索引に載っていない**ことを確認済み。

## 目的 / ゴール

DDS ビジュアルエディタの中だけで、画面・帳票に**罫線・枠を配置・確認・削除**できる状態にする。
テキストエディタに切り替えて座標を手計算する必要がない状態。

紐づく charter ゴール: **DDS（DSPF/PRTF）の視覚的な確認と編集**（第4の柱）
——「プレビュー上での配置編集（移動・長さ変更・追加・削除）」に該当。

## ユーザーストーリー

- US1: DDS 画面/帳票の設計者として、プレビュー上で罫線・枠を見たい。なぜなら、
  現状はソースの `GRDLIN`/`BOX` 等の行を読んで頭の中で座標を組み立てる必要があり、
  他のフィールド・様式のようにプレビューだけで完結しないから。（受け入れ: AC2, AC3）
- US2: DDS 画面/帳票の設計者として、プレビュー上の操作で罫線・枠を新規に配置したい。
  なぜなら、桁・行を手で数えて `GRDLIN(行 列 行 列)` のような引数を書くのは
  既存のフィールド配置（ドラッグで置ける）に比べて明らかに退行した体験だから。
  （受け入れ: AC4, AC-I1〜I5）
- US3: DDS 画面/帳票の設計者として、置いた罫線・枠を選択して削除し、誤りは undo で
  戻したい。なぜなら、既存のフィールド・様式の削除と挙動が食い違うと学習コストが増えるから。
  （受け入れ: AC6）
- US4: この PJ の開発者として、GRD 系キーワードの原典の取りこぼしを機械検査で塞ぎたい。
  なぜなら、索引から辿れないキーワードが他にも残っている可能性があり、
  手作業の確認では再発を防げないから。（受け入れ: AC1, AC5）

## スコープ

### 対象

- DSPF の `GRDLIN`（線）/ `GRDBOX`（枠）の原典取得・キーワードデータへの反映。
- DSPF の `GRDLIN`/`GRDBOX` を描画モデル（`dspfRenderModel`）に反映し、プレビューに表示する。
- PRTF の `BOX`（枠）/ `LINE`（線）を描画モデル（`prtfRenderModel`）に反映し、プレビューに表示する。
- プレビュー上の操作で罫線・枠を新規に配置する手段（DSPF/PRTF 両方）。
- 配置済みの罫線・枠の削除、および undo による復元。
- GRD 系キーワードのような**索引からの取りこぼし**を検査で固定する仕組み
  （既存の `verify-dds-keywords.mjs` 系スクリプトの拡張、または同種の追加検査）。

### 対象外

- `GRDATR`（属性）/ `GRDCLR`（消去）の**作図 UI**。属性の変更・消去はレコード/フィールドの
  範囲を再定義する操作で、単純な線・枠の描画とは性質が異なる。キーワードデータとしては扱う
  （原典取得・補完の対象には含める）が、プレビュー上に描く対象にはしない。
- 罫線・枠を含む DDS が実機コンパイルを通るかの確認（作成直後のコンパイル経路はこの機能に
  無く、`20260908-dds-new-and-records` でも受け入れ基準に含めていない）。
- DSPF/PRTF 以外の DDS 種別（PF/LF）への罫線対応（罫線に相当するキーワードを持たない）。

## 機能要件

- DSPF: `GRDLIN`/`GRDBOX` の原典が取得され、キーワードデータ（補完・プロンプター等、
  既存キーワードと同じ経路）に反映されている。
- DSPF: `GRDLIN`/`GRDBOX` を持つソースを開くと、プレビュー上に線・枠が描画される。
- PRTF: `BOX`/`LINE` を持つソースを開くと、プレビュー上に線・枠が描画される。
- プレビュー上の操作で罫線・枠を新規に配置でき、対応する DDS ソース行が書き出される。
- 配置済みの罫線・枠を選択して削除でき、undo で追加前の状態に戻せる。

## 非機能要件 / 制約

- 桁・行の判定は `src/core/dds/` に一本化し、既存の判定ロジック（`ddsEdit.ts` /
  `dspfRenderModel.ts` / `prtfRenderModel.ts` 等）と重複させない
  （AGENTS.md「同じ概念集合を複数箇所で列挙しない」）。
- 桁・行の規定は**原典の生テキストと照合して確定する**（要約や記憶に頼らない）。
  原典に記述が無い挙動は実機（IBM i）で確かめ、確認手順を成果物に残す
  （charter の品質基準・AGENTS.md「原典と実機が食い違ったら、実機のパーサーに判定させる」）。
- 既存のプレビュー・編集・undo の挙動を壊さない（後方互換）。
- 標準構成（core / protocol / bridge / ui / host）を踏襲し、`vscode` への依存を core・UI に
  持ち込まない（`20260908-dds-new-and-records` の設計をそのまま延長する）。

      キーワードデータに反映している。取得元は原典の生テキストで裏付けている。
- [ ] AC2: `GRDLIN`/`GRDBOX` を含む DSPF ソースを開くと、プレビュー上に線・枠が描画される。
- [ ] AC3: `BOX`/`LINE` を含む PRTF ソースを開くと、プレビュー上に線・枠が描画される。
- [ ] AC4: プレビュー上の操作で罫線・枠を新規に配置でき、DDS ソースに対応する行が書き出される
      （DSPF/PRTF 両方）。
- [ ] AC5: 罫線・枠が占める桁・行の判定規則は、原典の生テキストと照合して確定している
      （境界値・桁の単位を含む）。
- [ ] AC6: 配置済みの罫線・枠を削除でき、undo で追加前の状態に戻せる。
- [ ] AC7: GRD 系を含む「索引に載らないキーワード」の取りこぼしを機械検査で検出できる
      （検査が無ければ FAIL する形で固定されている）。

## 相互作用の受け入れ基準

罫線・枠の新規配置はプレビュー上の操作を伴う部品のため記載する。
既存のフィールド配置・様式追加（`20260908-dds-new-and-records`）と挙動を揃えることを既定の想定とする
（design で具体化する）。

- [ ] AC-I1 開く / 閉じる: 罫線・枠を配置する操作の開始・終了の手段があり、既存の
      追加操作（＋ボタン等）と一貫している。
- [ ] AC-I2 確定 / 取り消し: 配置操作は明示的な確定で反映され、取り消し（Escape 等）では
      何も残らない。
- [ ] AC-I3 キーボードだけで完結するか: マウスでのドラッグだけでなく、既存のフィールド
      移動・リサイズと同じ手段（矢印キー等）で始点・終点を指定して配置できる。
- [ ] AC-I4 フォーカスの行き先: 配置後は新しく置いた罫線・枠へ焦点が移り、取り消したら
      元の位置に焦点が戻る。
- [ ] AC-I5 既存の操作を妨げないか: 罫線・枠を配置する操作中のキー入力が、選択中の
      他の要素（フィールド等）へ漏れない。

## 未確定事項 / 確認したいこと

- **GRDLIN/GRDBOX の原典の所在**（索引に無い場合、どこから機械的に取得するか）。
  解消できなければ「原典に記述が見当たらない」という事実自体を記録し、実機確認で補う
  （research 工程で扱うことを推奨——下記参照）。
- 罫線・枠を配置する具体的なジェスチャー（ドラッグの始点/終点の与え方、キーボードでの
  始点/終点の指定方法）は design で確定する。
- DSPF と PRTF を 1 つの work のまま進めるか、tasks 工程の分割判定（3層決定木）で
  subtask に割るかは、この工程では決めない（design の後、tasks で判定）。
