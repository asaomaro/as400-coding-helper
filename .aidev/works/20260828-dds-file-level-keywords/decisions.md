# 決定記録

## D1: `toLogicalUnits` の返す形は変えない

- 背景: ファイル・レベルの行が捨てられているのが原因。素直には
  `toLogicalUnits` に含めることになる。
- 決定: **含めない。** 別の口（`fileLevelKeywordLines`）から読む。
- 理由: 読み手（`resolveDspfLayout` / `resolvePrtfLayout` / `buildDspfOutline` /
  `ddsEdit`）はどれも「単位＝置けるもの」を前提にしている。混ぜると**置こうとする**
  ——位置欄が空なので `missing-position` が並ぶ、といった形で壊れる。
- 影響: 読み手を 1 つも変えずに済んだ。

## D2: 分類の規則を切り出す（`classifyDdsLine`）

- 背景: 新しい読み手も「様式か / 項目か / 条件だけか / キーワードだけか」を判断する。
  写すと、**同じ行が片方では様式・片方ではキーワード**になりうる。
- 決定: `classifyDdsLine(line, keywords)` に切り出し、`toLogicalUnits` も使う。
- 注意: 引数の `keywords` は**継続を解いたあとの機能欄**。生の欄を渡すと、
  継続元の行が定数と読めない（引用符が閉じていないため）。

## D3: 読むだけ。編集は出さない

- 背景: 様式・項目のプロパティはチップから編集できる（`✕` / `＋` / 生テキスト）。
- 決定: ファイル・レベルは**読み取り専用**。
- 理由: 編集（`setKeywords`）の宛先は論理単位で、ファイル・レベルの行は単位にならない
  ——送っても `line-not-found` で断られる。**効かない操作を出さない**。
- 影響: 編集できるようにするなら `setKeywords` の宛先を広げる必要がある。別項目に起票。

## D4: 一覧のクラス名を既存と共有しない

- 背景: 最初は見出しに `record`、行に `item` を付けた。
- 決定: `file-level` / `file-keyword` にする。
- 理由: **共有した瞬間に壊れた**——e2e で「一覧の最初の項目を選ぶ」経路が
  ファイル・レベルの行を拾い、「様式を選ぶ」経路が「ファイル」の見出しを拾った。
  これらは項目でも様式でもないので、クラスも分ける。
- 影響: 見た目は `.file-level` / `.file-keyword` に独自に書いた。
