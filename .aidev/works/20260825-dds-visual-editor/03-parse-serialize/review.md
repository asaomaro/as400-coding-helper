### 指摘

#### should-1: BOM 付きファイルだけ「黙って化けさせない」原則が破れている

`decodeSource` の BOM 経路が**非 strict でデコードし、警告を返さない**。
BOM 無しの同じ壊れ方では警告が出るのに、BOM が付くと出ない。**同じ関数の中の不整合**。

実測:

```
BOM 付き + 壊れたバイト → encoding: utf8 / warning: (なし) / text: "A��\n"
BOM 無し + 同じ壊れ方   → warning あり
```

`text/decode.ts` の設計コメントは「黙って化けさせない（spec エラー処理）」と明記しており、
**実装が自分の宣言を守れていない**。

対応: BOM 経路でも strict を試し、失敗したら非 strict ＋警告にする。
「BOM があるので UTF-8 は確定」という判断は正しいが、
**エンコーディングの確定と、中身が妥当かの検査は別**。

#### should-2: 同名のレコード様式が現れると `itemIds` を共有してしまう

`itemsByRecord` を**レコード名でキーにしている**ため、同じ名前の様式が 2 回現れると
両方の `DdsRecord` が**同一の配列を参照**し、双方が全アイテムを自分のものとして主張する。

実測:

```
R REC1 / FLDA / R REC1 / FLDB
→ records: [{name:"REC1", items:["REC1#1","REC1#2"]},
            {name:"REC1", items:["REC1#1","REC1#2"]}]
```

同名の様式は DDS として不正なので実務では起きにくいが、
**壊れた入力に対してモデルが静かに嘘をつく**のは避けたい。
07 の様式ツリーや 04 の検証がこの配列を信じると、誤った結果を出す。

対応: `itemIds` を**レコードの出現ごと**に持つ（名前ではなく出現でキーにする）。
ID の一意性は `ordinals` が名前キーのままでも保たれる（`REC1#3`, `REC1#4` と続く）。

#### nit-1: 走査回数が多い

`classify` と `buildItem` で `fieldAt` / `sliceColumns` を 1 行あたり 10 回以上呼び、
そのたびに `text/encoding` の走査が 2 回走る（1 行あたり ~20 回の O(n) 走査）。
DDS の行は 80-132 桁、ファイルは数百行なので**現状の規模では問題にならない**。
02-encoding の nit-1 と同根で、必要になった時点で走査結果を持ち回る。**今は最適化しない。**

#### nit-2: `literalFromFunctions` は継続行にまたがるリテラルを扱えない

閉じ引用符が見つからない場合、取り出せた分だけを返す。継続行は `opaque` なので
リテラルの残りは別行にあり、`item.text` は不完全になる。
`keywords` に生テキストが残るので**情報は失われない**。L3（キーワード解釈）の担当。

#### nit-3: `DdsRecord.itemIds` の型が `readonly` だが実体は構築後に変更される

`parse` の中で配列を作ってから push で埋めている。外部からは不変に見えるので実害はないが、
型が実装を正確に表していない。should-2 の修正と同時に整理できる。

### 判定

**should 2 件**のため、coding へ差し戻す。

## ラウンド 2（2026-08-26・差し戻し対応後）

### 対応内容

- **should-1 解消**: BOM 経路でも strict デコードを先に試し、失敗したら非 strict ＋警告にした。
  **「エンコーディングの確定」と「中身が妥当かの検査」を分けた**のが要点。
  BOM があれば UTF-8 は確定してよいが、それは本文が壊れていないことを意味しない。
  回帰テストとして「**BOM の有無で警告の有無が変わらない**」を固定した。
- **should-2 解消**: `itemIds` をレコード名ではなく**出現ごと**に持つようにした
  （`currentItemIds` を様式宣言のたびに作り直す）。
  ID の採番は名前キーのままなので一意性は保たれる（`REC1#1`, `REC1#2` と続く）。
  回帰テストで「出現ごとに別々の `itemIds`」「ID が重複しない」を固定した。
- **nit-3 も同時に解消**: `itemIds` の構築が 1 か所（`currentItemIds`）に閉じ、
  複数の `DdsRecord` が同じ配列を参照する構造が無くなった。
- nit-1（走査回数）/ nit-2（継続行にまたがるリテラル）は**修正しない**。
  前者は 02-encoding の nit-1 と同根で、必要になった時点で対処する。
  後者は `keywords` に生テキストが残り情報が失われないため、L3 の担当。
