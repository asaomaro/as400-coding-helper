### 指摘

#### should-1: 幅を判定できない項目が、描かれず・検証もされず・誰にも知らされない

`itemWidth` が `undefined` を返す項目——**参照フィールド（`REFFLD` 等、長さ無し）**と
**キーワード駆動の項目（`DATE` / `TIME` / `USER` 等、リテラルを持たない定数）**——は、
`render` が描かず、`validate` も隣接判定から外す。**そこまでは意図どおり**（04 の should-1 で
「検証できないものは検証しない」と決めた）。

問題は**誰にも伝えていない**こと。実測:

```
DATE EDTCDE(Y) を 5 行 2 桁に置いた DDS
→ kind: constant / text: undefined / itemWidth: undefined
→ 描画: 空白 / 診断: []（何も出ない）
```

実機にはその位置に日付が出る。**キャンバスが実機と違って見えるのに、理由がどこにも示されない。**
利用者は「エディタが壊れている」と受け取るしかない。

対応: **配置されているのに幅を判定できない項目に診断（警告）を出す**。
`DDS7107` を足し、「この項目は内容を判定できないため描画・検証の対象外」と伝える。
07（GUI）はこれを見てキャンバス上に「解釈不能」として示せる。

#### should-2: `record` を省略すると複数様式が重なり、意味のない絵になる

`renderAscii` は `record` 省略時に**配置済みのアイテムをすべて描く**。
DSPF は複数の様式が同じ領域を使うのが普通なので、結果は重なって潰れる。実測:

```
R1 に 'AAAAAAAAAA'(3 行 2 桁)、R2 に 'BBB'(3 行 2 桁)
→ 3 行目: " BBBAAAAAAA"
```

**どちらの様式の内容かも、重なっていることも分からない。** これが既定というのは危うい。
`dds render <file>` を `--record` 無しで叩いた利用者（06 の想定利用）がこれを受け取る。

対応: **既定を「最初の様式」にする**。全部を重ねたいときは明示的に指定させる。
requirement Q2b で決めた「重ね合わせは確認用・アクティブ様式は 1 つ」という方針とも揃う。

#### nit-1: `EDTCDE` / `EDTWRD` を持つ数値フィールドは表示幅が `length` と異なる

実機では `EDTCDE(J)` 等が桁区切りや符号を足すため、`length` より広く表示される。
現状は `length` のまま描く。

**ただし本 subtask では直さない。** キーワードは未解釈で保持する設計（spec）であり、
DDS 原典も未収集（research F14）。**「EDTCDE があるから幅が違うはず」と推測して補正するのは、
根拠のない実装**にあたる（AGENTS.md の検証規約が戒めている類）。
L3（キーワード編集）で原典を収集したときに正しく扱う。**限界として deliver に引き継ぐ。**

#### nit-2: `DSPSIZ` キーワードを読まないため、画面サイズは呼び出し側が指定する必要がある

DDS の `DSPSIZ(24 80 *DS3)` に画面サイズが書いてあるが、キーワードは未解釈なので読めない。
既定の 24×80 と違う画面（27×132）では呼び出し側が `screen` を渡す必要がある。
nit-1 と同じく L3 の範囲。
