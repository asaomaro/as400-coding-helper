# 決定記録

## D1: 出力形式を自分で決めず、実機 `get_screen` の形に合わせた

- 背景: ゴールデンの形式を先に決めてから実機のキャプチャを変換する、という順序もありえた。
- 決定: **先に実機の `get_screen` を叩いて形式を実測し、レンダラをそれに合わせた**。
  各行きっかり 80 JS 文字 / 全角は「文字＋空白」の 2 セル / SO・SI・属性バイトは空白。
- 理由: 形式を自分で決めると「レンダラの出力とゴールデンを揃える変換」がもう 1 段必要になり、
  **その変換がバグの温床になる**。実機の形に合わせれば変換が要らず、比較が素直な文字列比較になる。
- 影響: `render/ascii` の出力契約が実測に基づくものになった。

## D2: フィールドにはプレースホルダと同じ値を実機に描かせる（加工しない）

- 背景: レンダラはプレースホルダ（`X` / `9`）を描くが、実機には実行時の値が出る。
  そのまま比較すると必ず食い違う（plan R1）。
- 決定: **CL ドライバでフィールドにプレースホルダと同じ値を書き込み、実機に実際に描かせる**。
  英数字 → `'XXXXX'`、数値 → `9999`。
- 理由 / 代替案: 代替は「実機キャプチャのフィールド領域をプレースホルダに置換してからゴールデン化」。
  だが**加工すると、加工の側にバグが入っても気付けない**。
  実機が描いたものをそのまま保存できるほうが、ゴールデンテストの意味が保たれる。
- 影響: CL ドライバに「プレースホルダと同じ値を入れる」という制約が生まれた。
  **実際にここを踏んだ**——最初 `FLD2` に `'YYYYYYYY'` を入れて比較が落ち、ドライバを直して採り直した。
  手順書（`docs/dds-golden/README.md`）に注意として明記した。

## D3: 数値型の判定は 35 桁目のデータ型で行う

- 背景: プレースホルダを `X` と `9` で出し分けるために、数値型を判定する必要がある。
- 決定: 35 桁目が `S` / `Y` / `N` / `P` / `B` / `F` のいずれかなら数値とみなす。
- 理由: DDS 原典が未収集（research F14）なので、**この集合は網羅的である保証がない**。
  ただし外れても影響は「プレースホルダの見た目」だけで、桁位置には影響しない。
  L3（キーワード編集）で原典を収集したときに見直す。
- 影響: 未知の型は英数字として扱われる（`X` が出る）。桁は正しい。

## D4: レンダラは画面外・幅不明のアイテムを黙って描かない

- 背景: 行が画面外、長さが不明（参照フィールド）といったケースの扱い。
- 決定: **描かない**。エラーにも警告にもしない。
- 理由: **検証は `validate` の担当**で、レンダラが二重に判定すると責務が混ざる。
  レンダラは「描けるものを描く」に徹し、問題の指摘は `validate` の診断に一本化する。
- 影響: テストで「描かれない」ことを固定した。

## D5: 差分出力に手をかけた

- 背景: 80×24 の文字列を丸ごと出されても、どこが違うのか分からない。
- 決定: 不一致時に「**何行目の何桁目から違うか**」と、その前後 30 文字を出す。
- 理由: ゴールデンテストの価値は**落ちたときに原因が分かること**にある。
  一致するだけなら形式は何でもよいが、落ちたときに読めないと調査が止まる。
- 影響: `golden.test.ts` に専用の比較関数を置いた。
