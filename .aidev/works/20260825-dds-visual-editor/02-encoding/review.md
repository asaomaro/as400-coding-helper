### 指摘

#### should-1: `displayWidthOf` が `displayWidth` の単なる別名で、座標系の区別に寄与していない

design の「換算 API の適用先を語彙で分ける」に従って 3 つのラッパを足したが、
そのうち `displayWidthOf` は**区別を生んでいない**。

- `charIndexToSourceColumn` / `sourceColumnToCharIndex` は
  「**ソース行内の桁**」という座標系 1 を名前で示しており、意味がある。
- 一方 `displayWidthOf` は `displayWidth` と**同じ座標系・同じ計算・同じ引数**で、名前だけが違う。

**両方を export していることが問題**で、呼び出し側がどちらを使うか揺れる。
語彙で強制するはずの仕組みが、逆に「同じことをする 2 つの名前」を生んでいる。

対応: **`displayWidthOf` を削除し、`displayWidth` を座標系 2 の正式名とする。**
座標系の区別は「ソース行用のラッパがある / 素の関数は画面用」という非対称で表現し、
その旨をモジュールの JSDoc に明記する。design の意図（語彙で取り違えを防ぐ）は満たしつつ、
冗長な別名を持たない。

#### nit-1: `scan` が公開 API の呼び出しごとに走る

`displayWidth` / `charIndexToColumn` / `columnToCharIndex` / `sosiPositions` は
いずれも内部で `scan(text)` を呼ぶため、同じ文字列に対して繰り返し呼ぶと O(n) が毎回走る。
DDS の行は 80〜132 桁で、レンダリング対象も数十アイテムなので**現状の規模では問題にならない**。
ただし 07-editor-webview で全アイテムを毎フレーム再計算する作りにすると効いてくる。
必要になった時点で `scan` の結果を持ち回す形にすればよい（**今は最適化しない**）。

#### nit-2: 後続サロゲートを指されたときのフォールバックが線形後方走査

`charIndexToColumn` は `startColumn[index] === -1` のとき直前の開始桁を探して後ろへ走査する。
サロゲートペアは 2 コード単位なので実際には 1 回で止まるが、ループの形をしているため
「任意長を戻りうる」ように読める。**EBCDIC に対応字が無く実務では現れない経路**なので実害はない。

#### nit-3: `Occupant.index` の意味が種別によって変わる

`kind: "si"` のとき `index` は「run 直後の索引（末尾なら `text.length`）」を指し、
`"char"` / `"char-tail"` / `"so"` のときとは意味が違う。JSDoc には書いてあるが型では表現されていない。
内部型なので実害はないが、将来 `occupant` を公開するなら判別可能ユニオンにすべき。
