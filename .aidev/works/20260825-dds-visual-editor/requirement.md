# 要件: DSPF/PRTF ビジュアル編集（DDS ビジュアルエディタ）

## 背景 / 課題

- DSPF/PRTF の DDS は固定長フォーマットで、**桁位置・条件標識・レコード様式の重なりを頭の中で組み立てながら**
  書く必要がある。実機の SDA は 5250 端末上でしか使えず、VSCode の開発フローから分断される。
- 本拡張は既にルーラー表示と SOSI 表示で「SEU と同じ桁位置で見せる」ところまで支援しているが、
  `.dspf` / `.prtf` に対しては**表示支援のみ**で、レイアウトを組む手段が無い
  （`vscode-extension/src/utils/fileScope.ts` の `TARGET_EXTENSIONS` に入っているだけ）。
  DDS のパーサ・モデル・プロンプター定義はいずれも存在しない。
- **AI エージェントが DDS を扱う手段も無い。** テキストとして読み書きするしかなく、桁計算・標識・様式構造を
  毎回推論することになり、誤りが出る。しかも**誤りに自分で気づけない**。
- 一方、検証手段としては **ts5250 エミュレータ（MCP）**が利用でき、実機で DDS をコンパイル・表示して
  「実際どう見えるか」を機械的に採取できる。DDS ビジュアル編集の正しさは実機の見え方が唯一の正解なので、
  ここに直結させられる。

## 目的 / ゴール

達成したい状態:

- **DSPF/PRTF のレイアウトを、桁位置を手で数えることなくマウス操作で組み立てられる状態。**
- **エディタの描画が実機の見え方と一致していることを、機械的に確認できる状態。**
- **人間（GUI）と AI エージェント（CLI / MCP）が、同一のコアを通じて同等の編集能力を持つ状態。**
- **既存の手書き DDS を開いて一部を編集しても、触っていない行が 1 バイトも変化しない状態。**
- **AI エージェントが、要求から DDS を起案し、自己検証して修正まで到達できる状態。**

紐づく charter ゴール:
- 「**DDS（DSPF/PRTF）のビジュアル編集**を第4の柱として加える」（2026-08-25 に本 work のため追加）
- 「上記を支える **VSCode 非依存の基盤ツール**（ライブラリ / CLI、将来的に MCP）を併せて整備し、
  人間（GUI）と AI エージェント（CLI/API）の双方が同じコアを使える状態にする」（同上）

> charter の non-goal「実験的な UI 刷新・SEU 互換を超える独自機能」に対しては、
> **本機能を明示的な例外**として記録済み（SEU/SDA 相当をマウス操作で置き換える意図。他機能へ拡大しない）。

## スコープ

本 work の完了条件は **walking skeleton（縦に薄く一周させる）** に置く。
ゴール全体（下記「ゴール範囲」）は requirement として記録し、横展開は後続 work で積む。

### 対象（本 work）

- **DSPF のみ**。単純な 1 レコード様式（条件標識なし・サブファイルなし）を対象とする。
- DDS 固定長**パーサ / モデル / シリアライザ**（無編集行のバイト保存を含む）。
- **表示桁（EBCDIC 換算） ⇄ ソース文字位置**の換算（SO/SI の扱いを含む）。
- **ASCII レンダラ**（CLI と GUI とゴールデン比較が同一実装を使う）。
- **L1 編集**（フィールド / 定数の移動・リサイズ・追加・削除）。
- **CLI**: `parse` / `render` / `validate` / `patch`。
- **VSCode カスタムエディタ**（`priority: "option"` 登録・最小 GUI・テキストエディタと双方向同期）。
- **実機ゴールデン検証基盤**（record/replay）と代表フィクスチャ一式。

### 対象外（本 work。ただしゴールには含む＝後続 work）

- **L2〜L5**: 基本属性（名前/長さ/型/使用/参照）、キーワード編集（`DSPATR` `EDTCDE` `COLOR` `SPACE/SKIP` 等）、
  レコード様式の追加/削除/並べ替え、条件標識の付け外し、サブファイル（SFL/SFLCTL）・ウィンドウ・機能キー。
- **PRTF 全般**（様式＝バンド編集）。
- **MCP サーバ**（同一コアに皮を被せる形で後続）。
- **複数様式のレイヤー表示**（表示する様式の選択、アクティブ様式のみ編集可、標識セット切替による描画反映）。

### 対象外（ゴールにも含めない）

- **PRTF のページ合成プレビュー**（実行時のプログラム制御に依存し、静的には確定できないため）。
- **EBCDIC 生バイトファイルの直接読み書き**（CCSID 変換・転送は別の道具の責務）。
- **製品機能としての実機ランタイム連携**（接続・コンパイル・実行）。charter の non-goal のまま。
  実機は**開発時の検証手段としてのみ**使う。
- **フリーフォーマット RPG 対応**（charter non-goal。本 work とは無関係だが念のため）。

### ゴール範囲（本 work 完了後に目指す全体像）

L1〜L5 のフル GUI ＋ DSPF/PRTF 両対応 ＋ headless コア ＋ CLI ＋ MCP ＋ ゴールデン検証基盤。
UI は **共通シェル＋種別プロファイル**（キャンバスの意味・語彙・検証ルールを DSPF/PRTF で差し替え）とし、
ユーザーからは種別ごとの専用デザイナに見える。

## 機能要件

本 work（walking skeleton）で満たすもの:

1. `.dspf` を読み、レコード様式・フィールド・定数・キーワードを**構造化モデル**に変換できる。
2. モデルを DDS へ書き戻せる。**編集していない行はバイト単位で不変**である。
3. 解釈できない行・未対応キーワードは **opaque として保持**し、書き戻しで失わない。
   （原則: **扱えない要素があることは許容するが、扱えない要素を壊すことは許容しない**）
4. 座標を**表示桁**（DBCS = 2 桁、SO = 1 桁、SI = 1 桁）で扱い、ソース文字位置と相互換算できる。
5. レコード様式を **ASCII で描画**できる。CLI・GUI・ゴールデン比較が**同一のレンダラ実装**を使う。
6. GUI 上でフィールド / 定数を**移動・リサイズ・追加・削除**できる（L1）。
7. **桁溢れ・フィールド重なり・DDS 規則違反**を検証できる。
8. CLI から `parse` / `render` / `validate` / `patch` を実行でき、`patch` の編集能力が **GUI の L1 と同等**である。
9. VSCode で `priority: "option"` 登録され、テキストエディタと**並べて双方向同期**できる。
10. **UTF-8 と Shift_JIS** のソースを読み、同一のモデルを得る。

## 非機能要件 / 制約

- **headless コアは `vscode` に依存しない。** ディレクトリ境界を引き、**依存の不在を機械的に検証**する
  （既存 29 ファイル中 25 が `vscode` を import しており、本 work がこの層構造の第一号になる）。
- **既存挙動を壊さない**（charter 品質基準）。`.dspf` / `.prtf` の既定エディタを奪わず、
  ルーラー表示・SOSI 表示は従来どおり動作する。
- **`languageId` を新設・拡大しない。** 表示系は拡張子判定で有効化するという既存方針を維持する
  （AGENTS.md「languageId / アクティベーション変更時の下流波及チェック」）。
- **実機接続を CI の必須依存にしない。** 実機はゴールデンの採取・更新時のみ使い、
  日常のテストと CI はコミット済みゴールデンとの比較で回る。
- **仕様の根拠は IBM 原典の生テキストと照合**する。DDS キーワードの仕様は要約や知識で代替しない。
  この照合は**主エージェントが直読**する（AGENTS.md 開発時の検証規約）。
- **1 PR = 独立してレビュー可能な粒度**（charter）。ゴール全体は 1 PR に収まらないため、
  **plan 工程で subtask 分割（protocol 2.8）または複数 work への分解を必ず判定する**。
- GUI と CLI は**同一コアの同一操作**を叩く。編集モデルを二重に持たない。

## 未確定事項 / 確認したいこと

**research 工程で解消すべきもの（調査対象）:**

- **実運用の DDS ソースに SO/SI の実バイトが入るのか、UTF-8 日本語で持つのか。**
  既存 `dbcsShiftMarkers.ts` は実バイトを読まず、Unicode コードポイントで DBCS 連続範囲を検出して
  `{` `}` を装飾として重畳している。**実機のソースメンバを直読して確定させる**。
  表示桁換算の設計がこれに依存するため、推測で決めてはならない。
- **DDS キーワードリファレンスの原典が `docs/origin/` に未収集。**
  `CRTDSPF` / `CRTPRTF`（CL コマンド）はあるが、DDS そのものの原典が無い。
  AGENTS.md の検証規約に従い収集する。
- **実機検証の手順確立**: `CRTDSPF` → 表示 → キャプチャ → ゴールデン化の一連の流れ。
- **リポジトリに DSPF/PRTF のサンプルが 1 つも存在しない**（`docs/src/` は `.clp` と `.rpgle` のみ）。
  代表フィクスチャをゼロから作る必要がある。
  なお既存サンプル RPG は 2 本とも**サブファイルを使用**している
  （`EMPMNT01.rpgle:15` `SFILE(EMPSFL:RRN)` / `SLSENT01.rpgle:28` `SFILE(DTLSFL:RRN)`）ため、
  ゴール範囲ではサブファイル対応が実質必須。

**ユーザーに確認したいもの:**

- **実機検証にどのシステムを使うか。** `list_systems` は `srv:PUB400`（pub400.com）と
  `srv:SR-OSAKA`（172.21.10.51）を返す。社内機に接続する話になるため、research 着手時に確認する。
- **Q7 と Q10 の整合**: MCP サーバは**ゴールには含むが、本 work の完了条件には含めない**という整理でよいか。

**spec / design 工程へ送るもの:**
