### 指摘

#### must-1: 既存のエラーがある DDS は、無関係な箇所も一切編集できない

`applyOps` は適用後に**文書全体**を検証し、エラーが 1 つでもあれば拒否する。
そのため**パッチ以前から存在するエラー**も拒否の理由になり、
**そのファイルは実質読み取り専用になる**。

実測:

```
BAD(70 桁から 20 桁 = 89 桁で桁溢れ) を含む DDS
→ 既存の診断: DDS7101/error
→ 無関係な OK1 を動かすだけの操作が拒否された
```

これは requirement **US2（既存資産を保守する開発者として、手書き DDS を開いて一部だけ直したい）を
真っ向から否定する**。しかも実務の DDS ほどエラーを含んでいる可能性が高く、
**この機能が最も必要な相手にこそ使えない**という最悪の形になる。

plan R1 で「警告で止めるな」と自分に釘を刺していたが、
**「元からあるエラーで止める」という同じ種類の失敗を見落としていた。**

対応: **パッチが触ったアイテムに生じたエラーだけで拒否する**。
エラー級の診断（桁溢れ・行範囲外・長さ欄溢れ）は**アイテム単位で独立**しているので、
touched な行に紐づく診断だけを見れば足りる。

#### should-1: 長さの無いフィールドが幅 0 として扱われ、検証が黙って素通りする

`itemWidth` はフィールドについて `item.length ?? 0` を返す。
**参照フィールド（`REFFLD` 等、長さを DDS に書かないもの）は `length` が undefined** なので幅 0 になり、
桁溢れも隣接も検出されない。

実測:

```
REFFLD（長さ無し, 2 桁目）+ NEXT（5 桁, 3 桁目）
→ itemWidth(REFFLD) = 0 → 診断なし
```

実際には REFFLD の幅次第で隣接違反になりうるが、**幅 0 と決めつけて素通りしている**。
実務の DDS は参照フィールドを多用するため、**誤った安心を与える**。

対応: **幅が不明なアイテムは隣接判定から除外する**（幅 0 と扱わない）。
除外していることをコードとドキュメントで明示し、
「検証できないものを検証したふりをしない」状態にする。

#### nit-1: 桁が 1 未満のときに `overflow` コードを使っている

`item.pos < 1` を `DDS7101`（桁溢れ）で報告しているが、意味が違う（不足であって溢れではない）。
実害は無いが、コードから理由が読み取れない。

#### nit-2: 隣接判定が連続する 2 要素しか比較しない

桁順に並べて隣同士だけを比較するため、**非常に幅の広い要素が 2 つ以上先の要素と重なる**場合、
その組み合わせは報告されない。ただし各要素は直前の要素との比較で何らかの診断を受けるため、
**見逃しではなく報告の粒度の問題**。実機も 1 件にまとめているので実害は小さい。

#### nit-3: `insertionPoint` は同名レコードの最初の出現を選ぶ

同名のレコード様式が複数あると、`addItem` は常に最初の様式へ足す。
同名様式は DDS として不正なので実務では起きにくい（03 の review で同種の指摘済み）。

### 判定

**must 1 件 / should 1 件**のため、coding へ差し戻す。

## ラウンド 2（2026-08-26・差し戻し対応後）

### 対応内容

- **must-1 解消**: 拒否の判定を**このパッチが触った行に生じたエラー**だけに限定した。
  `rebuild` が「新しい配列での touched な行番号」を返し、`applyOps` はその範囲の
  エラーだけで拒否する。エラー級の診断はアイテム単位で独立しているので、この限定で足りる。
  **元からのエラーは診断には残す**（隠さない）が、編集はブロックしない。
  回帰テストで「元からエラーを含む DDS でも無関係な編集は成功する」
  「触った行に新しくエラーを作る操作は拒否される」「元からのエラーは診断に残る」を固定した。
- **should-1 解消**: `itemWidth` の戻り値を `number | undefined` にし、
  **幅が不明なアイテムを隣接判定から除外**した。参照フィールド（`REFFLD` 等）がこれに当たる。
  幅 0 と決めつけると、実際には違反している配置を素通りさせて**誤った安心を与える**。
  「検証できないものは検証しない——**できたふりをしない**」という方針をコードに明記した。
- **nit-1 解消**: 桁が 1 未満のケースに専用コード `DDS7106`（`posOutOfRange`）を割り当てた。
- nit-2（連続 2 要素しか比較しない）/ nit-3（同名様式の最初の出現を選ぶ）は**修正しない**。
  前者は各要素が直前との比較で診断を受けるため見逃しではなく粒度の問題で、実機も 1 件にまとめている。
  後者は同名様式が DDS として不正なため（03 の review で同種の指摘を記録済み）。

## ラウンド 3（2026-08-26・07 からの差し戻し対応）

### 対象

`patch/ops.ts` の拒否規則の変更（`decisions.md` D6）と、その回帰テスト 4 本、
およびフィクスチャ `dbcs-const.dspf` / `dbcs-const.sjis.dspf` の小数桁補正。

### 観点と結果

- **spec 適合**: spec は「検証違反を**生む**パッチは適用前に拒否」。
  「増えたエラーだけで拒否」は文面に忠実で、旧規則（触った行のエラー）より厳密に近い。**適合。**
- **判定鍵の妥当性**: 行番号・ID で突き合わせないのは `addItem` / `removeItem` で
  行がずれ ID も振り直されるため（D3）。**コードごとの件数比較は、この制約下で取れる唯一の安定な鍵。**
- **抜け道の明示**: 「1 件直して 1 件増やす」（同一コード・件数同じ）は素通りする。
  コード内コメントと D6 に明記済み。診断は `ApplyResult.diagnostics` で必ず返るので**隠れない**。
- **拒否理由の質**: 増えたコードの診断すべてが候補になるが、**触った行のものがあればそれを返す**。
  利用者に近い原因が出る。07 の GUI で状態表示に出ることを e2e で固定した。
- **費用**: `applyOps` ごとに `validate` が 1 回増える（適用前の分）。
  対象は 1 メンバのソースで、CLI / GUI の 1 操作あたり数十行〜百行規模。**許容。**
- **フィクスチャ補正**: `EMPNO 6S` / `DEPTCD 3S` の 36-37 桁に `0` を入れた。
  実機で `CPD7408` になる材料をテストに使っていた（07 `decisions.md` D12）。
  UTF-8 版と Shift_JIS 版の**両方**を同じ桁で直し、`dds validate` が「問題なし」を返すことを確認。
  AC10（両エンコーディングが同一モデル）のテストも通過。
