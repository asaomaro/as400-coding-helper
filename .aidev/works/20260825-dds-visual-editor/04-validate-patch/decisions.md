# 決定記録

## D1: 実データの重なりと属性バイトの隣接を別コードで報告する

- 背景: spec は「重なり」を 1 つの概念として扱っていたが、実装してみると 2 種類ある。
  - **実データそのものが重なっている**（`b1 <= a2`）
  - **データは重なっていないが、属性バイトぶんの空きが無い**（`a2 < b1 < a2 + 2`）
- 決定: 前者を `DDS7102`、後者を `DDS7103` として**別コード**で報告する。**重大度はどちらも警告**。
- 理由: 利用者にとって直し方が違う。前者は「片方を大きく動かす」、後者は「1 桁ずらす」。
  同じコードにすると、GUI が出す修正案を分けられない。
  実機はどちらも `CPD7866` にまとめているが、**エディタは実機より親切にしてよい**
  （重大度を変えているわけではないので、実機との整合は保たれる）。
- 影響: `DIAGNOSTIC_CODES` が spec の記述より 1 つ多い。

## D2: `applyOps` を「先に全解決 → 最後に一度だけ組み立て」の 2 段階にした

- 背景: 最初は行の配列を操作ごとに書き換え、削除・挿入による**索引のずれを持ち回る**実装にした。
  ずれ計算が複雑で、正しさに自信が持てなかった。
- 決定: **元のモデル上で全操作を解決**（差し替え / 削除 / 挿入をそれぞれ記録）してから、
  最後に一度だけ行の配列を組み立てる。
- 理由: **索引のずれ計算そのものが要らなくなる**。すべての操作が「元の行番号」を基準に解決されるので、
  操作の順序にも依存しない。加えて「**部分適用しない**」が自然に満たされる
  ——組み立ての前に throw すれば、何も起きていない。
- 影響: なし（外部から見た挙動は同じ。実装が単純になった）。

## D3: ID の振り直しを「隠さず、テストで固定する」

- 背景: `applyOps` は再パースして新しいモデルを返すため、構造を変えると ID が振り直される。
  これは仕様として受け入れる（plan「ID の安定性」）が、**黙っていると事故になる**
  ——古い ID を使い続けると別のアイテムを操作してしまう。
- 決定: **振り直しが起きることをテストで明示的に固定**した
  （`EMPMNT#1` を消すと元の `EMPMNT#2` が新しい `EMPMNT#1` になることを assert している）。
  あわせて「構造を変えなければ ID は不変」も固定した。
- 理由: この手の制約は「ドキュメントに書いた」だけでは守られない。
  **テストが仕様の説明になっている**状態にする。
- 影響: 07（GUI）と 06（CLI）は、構造変更後に ID を取り直す実装にする必要がある。

## D4: research.md F7 を訂正した（証拠の帰属誤り）

- 背景: research F7 に「`SRCDTA` は CCSID 1027 と宣言されているのに DBCS が混在している」と
  書いていたが、**証拠の帰属が誤り**だった。
- 決定: `QSYS2.SYSCOLUMNS` で確認し直し、`research.md` の F7 を訂正した。
  - `ASAOLIB/QDDSSRC` の `SRCDTA` = **CCSID 1027**（DBCS を含む member は無い）
  - `ASAOLIB/QJPNTEST` の `SRCDTA` = **CCSID 5035**（SO/SI を含む `JPNATTR` はこちら）
- 理由: 承認済み成果物であっても、**事実誤認は放置しない**。
  下流の判断（デコードを宣言 CCSID に依存させない）は訂正後も妥当だが、
  根拠が間違ったまま残ると後で別の判断を誤らせる。
- 影響: `research.md` F7 を書き換えた。設計・実装への影響はない。

## D5: 定数の幅は `displayWidth`（SO/SI 込み）でよい — 実機が裏付けた

- 背景: spec D7 に「DBCS を含む要素での属性バイトの扱いは未検証」と残していた。
- 決定: 実機で `CRTDSPF` を実行し、**コンパイラ自身の "Expanded Source" が
  `'社員番号'` を `Field length = 10` と報告する**ことを確認した。
  SO(1) + 全角 4 文字 × 2 + SI(1) = 10 で、`text/encoding` の `displayWidth` と完全に一致する。
  隣接規則 `b1 < a2 + 2` も DBCS 要素で 4 ケースすべて予測どおりだった。
- 理由: 推測で validate を書くと、**日本語画面でだけ誤検出する**という最悪の形になりうる。
- 影響: `spec.md` D7 の「未確定として残るもの」から DBCS の項目を消し、実測表を追記した。
  DBCS 用の特別扱いは実装に**不要**であることが確定した。

## D6: 拒否の規則を「触った行のエラー」から「**増えたエラー**」に変えた（07 からの差し戻し）

- 背景: 07 の GUI を Playwright で実操作したところ、**掴んでも動かないフィールド**があった
  （07 `decisions.md` D14）。原因は本 subtask の `applyOps`——「触った行にエラーがあれば拒否」
  という規則により、**元からエラーを持つ項目は動かせなかった**。
  小数桁の抜けたフィールドをレイアウト修正で動かす、という正当な操作が止まる。
- 決定: 適用前後で **エラーの件数がコードごとに増えたときだけ拒否**する。
  行番号や ID で突き合わせないのは、`addItem` / `removeItem` で行がずれ ID も振り直されるため
  （本 subtask D3）——「同じ診断か」を同定する安定な鍵が無い。
- 理由: spec の文面は「検証違反を**生む**パッチは適用前に拒否」。移動は違反を生んでいない。
  当初の規則は「元からエラーを含むファイルが編集不能になる」ことは避けていたが、
  **エラーを持つ項目自身**については同じ問題が残っていた。
- 影響: `patch/ops.ts` の判定を差し替え、回帰テストを 4 本追加した
  （元からエラーのある項目の移動・解消する移動・削除・同じコードのエラーが増える操作の拒否）。
  既存 218 テスト通過。**「1 件直して 1 件増やす」操作は素通りする**（件数が同じ）が、
  検証結果は `ApplyResult.diagnostics` で必ず返るので見えなくなるわけではない。
- 出自: ユーザー判断（2026-08-26）。07 の coding 中に本 subtask を coding へ差し戻して実施。
