# 要件: テスト対象をバインドして業務ロジックをテストできるようにする

## 背景 / 課題

RPGUnit は導入・実行・結果収集まで道具になったが、**テスト対象をバインドした実績が無い**。
これまで実機で通した 7 本を調べると、`BNDSRVPGM` / `MODULE` を**一度も指定していない**。

書いてきたのは全部**自己完結**のテストだった。

- `iEqual(2:2)` — 定数同士
- 0 除算で `MCH1211` — 自分で起こした例外
- `SELECT 42 FROM SYSIBM.SYSDUMMY1` — システムの定数表

つまり「**RPGUnit が動くこと**」は証明できたが、「**業務プログラムをテストできること**」は
まだ。単体テストの本体である「テスト対象をバインドしてその手続きを呼ぶ」経路が空白のまま、
周りだけ揃っている。

`tools/run-rpgunit.mjs` にも `BNDSRVPGM` を渡す口が無い。

## 目的 / ゴール

**自分のサービスプログラムの手続きを、テストから呼んで検証できる**状態。
かつ、そのテストが**本当に対象を見ている**ことが確かめられている状態
（対象を壊すとテストが落ちる）。

紐づく charter ゴール: 主要 3 本柱を支える検証基盤（`品質基準`「テスト通過」）。

## ユーザーストーリー

- **US1**: 本 PJ の開発者として、自分の書いた手続きをテストしたい。
  なぜなら、**それができないなら RPGUnit を入れた意味が無い**から。（AC1〜AC3）
- **US2**: 初めて RPGUnit を使う者として、**動く実例**が欲しい。
  なぜなら、プロトタイプの置き場所・バインドの指定・`/COPY` の解決は
  文章だけでは組み立てられないから。（AC4）
- **US3**: 道具を使う者として、`--bnd` の一言でバインドを指定したい。
  なぜなら、そこだけ手で `RUCRTRPG` を叩くなら道具の意味が薄れるから。（AC5）

## スコープ

### 対象
- `tools/run-rpgunit.mjs` に**バインド指定**（`--bnd`）を足す。
- **動く実例**（テスト対象のサービスプログラム ＋ プロトタイプ ＋ テスト）を用意する。
- 実例を実機で通し、**対象を壊すとテストが落ちること**まで確かめる。
- 手順を `tools/README.md` と skill `rpgunit-test` に書く。

### 対象外
- **テスト対象のビルド**（利用者自身の資産。道具はテストだけ作る）。
- `MODULE` によるバインド（`BNDSRVPGM` で足りる。必要になってから足す）。
- テストコードの自動生成（別項目）。

## 機能要件

- `--bnd <lib/name>` でテスト対象のサービスプログラムを指定でき、複数渡せる。
- 省略時は今までどおり（自己完結のテスト）。
- 実例は**固定長**で書く（本 PJ の対象）。

## 非機能要件 / 制約

- 実例は**実機で通ることを確かめたものだけ**を載せる（動かない例を置かない）。
- 実機にゴミを残さない。スプールは消さない。
- 既存の `--self-test` を壊さない。

## 完了条件 (受け入れ基準)

- [ ] **AC1**: テスト対象のサービスプログラムを用意し、その手続きを呼ぶテストが
      `--bnd` 付きでビルドでき、実行できる。
- [ ] **AC2**: そのテストが**合格**する（正しい実装に対して緑）。
- [ ] **AC3**: **対象を壊すとテストが落ちる**（`--bnd` が効いていることの証明。
      落ちないテストは何も守っていない）。
- [ ] **AC4**: 実例一式がリポジトリにあり、README の手順どおりに再現できる。
- [ ] **AC5**: `--bnd` を省略しても従来どおり動く（既存の実例で確認）。
- [ ] **AC6**: `--self-test` が通る（引数解析の追加分を含む）。

## 未確定事項 / 確認したいこと

- プロトタイプ（`/COPY`）の置き場所と解決のしかた（同じソース PF のメンバーで足りるか）。
- `CRTSRVPGM` の `EXPORT(*ALL)` で足りるか、バインダー言語が要るか。
